# สัปดาห์ 9: Vector Representation และ Semantic Search

## ภาพรวมใน 1 นาที

- ลองนึกถึงห้องสมุดที่ไม่เรียงหนังสือตามตัวอักษร แต่เรียงตาม "ความหมาย" หนังสือเรื่องใกล้กันอยู่ชั้นใกล้กัน
- เป้าหมายของสัปดาห์นี้คือทำให้ **ทุกประโยคมีพิกัดบนแผนที่ความหมาย** (เรียกว่า embedding หรือเวกเตอร์) ประโยคที่ความหมายใกล้กันต้องได้พิกัดใกล้กัน
- ปัญหา: BERT ดิบวางทุกประโยคไว้ในมุมเดียวกันของแผนที่ (เรียกว่า anisotropy) เลยแยกเรื่องที่เกี่ยวกับเรื่องที่ไม่เกี่ยวไม่ออก
- วิธีแก้: ฝึกเพิ่มแบบ SBERT ด้วย contrastive loss (สอนให้คู่ที่เหมือนกันยืนใกล้กัน คู่ที่ต่างกันยืนไกลกัน) แล้วใช้ mean pooling (เฉลี่ยเวกเตอร์ของทุกคำ) เป็นพิกัดของประโยค
- Bi-encoder ทำพิกัดให้ทุกเอกสารครั้งเดียวแล้วเก็บไว้ ค้นหาได้เร็ว ส่วน cross-encoder อ่านทีละคู่ละเอียดกว่าแต่ช้า จึงใช้จัดอันดับใหม่ในรอบสอง
- เมื่อมีพิกัดเป็นล้านชิ้น ต้องมีตู้เก็บและวิธีค้นที่เร็ว คือ FAISS กับ ANN (ยอมแม่นน้อยลงนิดหน่อยเพื่อเร็วขึ้นมาก) และต้อง normalize เวกเตอร์ก่อนเสมอ
- ผลลัพธ์ต้องวัดด้วย Recall@k (เจอคำตอบครบแค่ไหน) และ MRR (คำตอบถูกโผล่ขึ้นมาเร็วแค่ไหน)
- เรื่องราวสองประโยค: BERT ดิบทำพิกัดประโยคไม่ดีเพราะ objective ไม่เคยสอนเรื่องนี้ จึงฝึกเพิ่มแบบ SBERT ให้ได้พิกัดที่ดี จากนั้นเก็บพิกัดใน FAISS แล้วค้นด้วย bi-encoder ตามด้วย cross-encoder จัดอันดับใหม่ และวัดผลด้วย Recall@k กับ MRR
- ที่เหลือของบทเรียนคือรายละเอียดแต่ละชิ้น ถ้าไม่แน่ใจว่าจะเลือกเทคนิคไหน ให้ข้ามไปอ่านหัวข้อ "เลือกใช้เทคนิคไหน เมื่อไหร่ (สถานการณ์จริง)"

สัปดาห์นี้เป็นรากฐานของ RAG และของโปรเจกต์ทีม (dense retrieval ด้วย SentenceTransformers)

**แผนที่การอ่านสำหรับสอบ** ข้อสอบจริงคือวันจันทร์ที่ 9 พ.ย. 2569 เวลา 9:30-12:30 น. ปรนัย 70 ข้อ และเขียน 10 ข้อ ทุกสัปดาห์ได้ส่วนแบ่งข้อสอบเท่ากัน อาจารย์บอกว่าแล็บไม่ออก แต่สิ่งที่แสดงเฉพาะในเดโมอาจออกได้ 1-2 ข้อ ลำดับการอ่านที่แนะนำคือ หัวข้อ 5 (SBERT), 6 (loss), 4 (bi-encoder เทียบ cross-encoder), 2 (anisotropy), 9-10 (vector search), 11 (เมตริก) แล้วทำส่วน "โจทย์คำนวณตัวอย่างพร้อมวิธีทำ" ท้ายบทเรียน ส่วนข้อเท็จจริงที่มีเฉพาะในเดโมรวมไว้ในหัวข้อ "ข้อเท็จจริงที่มีในเดโมเท่านั้น" ท้ายบทเรียนก่อนสรุปมีสามส่วนสำหรับทบทวนก่อนสอบ คือ "คลังสูตรและค่าที่ต้องรู้" (ตารางสูตร ค่าคงที่ มิติ และ threshold ทุกตัวพร้อมเลขสไลด์), "ชุดฝึกคำนวณเชิงลึก" (22 ประเภทโจทย์ ทำเฉลยครบ รวมถึงกลับโจทย์และกับดักทศนิยม) และ "คู่ที่มักสับสนและตัวเลือกลวง" (ตารางคู่ที่สับสนและข้อความผิดแบบ "ข้อใดไม่ถูกต้อง")

## 1. ปัญหา: BERT ดิบ ๆ ทำ sentence vector ไม่ดี (สไลด์ 2-4)

> **พูดง่าย ๆ:** เราอยากให้ประโยคที่ความหมายเหมือนกันมีพิกัดใกล้กันบนแผนที่ BERT ดิบเหมือนแผนที่ที่ทุกจุดถูกวางทับกันมั่ว ๆ จึงค้นหาตามความหมายไม่ได้ SBERT คือวิธีวาดแผนที่ใหม่ให้ใช้งานได้

**ศัพท์ก่อนอ่าน:**

- embedding หรือเวกเตอร์ (ชุดตัวเลขที่เป็นพิกัดแทนความหมายของประโยค)
- token (ชิ้นคำย่อยที่โมเดลแบ่งจากประโยค)
- pooling (วิธีรวมเวกเตอร์ของหลาย token ให้เหลือ 1 เวกเตอร์ต่อประโยค)
- `[CLS]` (token พิเศษที่ BERT ใส่ไว้หน้าสุดของทุกประโยค)
- STS (Semantic Textual Similarity ชุดข้อมูลที่คนให้คะแนนความคล้ายของคู่ประโยค)
- Spearman ρ (ค่าวัดว่าการเรียงอันดับของโมเดลตรงกับอันดับที่คนให้ได้แค่ไหน ยิ่งสูงยิ่งดี)

เป้าหมายคือฟังก์ชัน `f: ประโยค → ℝ^d` ที่ประโยคความหมายใกล้กันต้องได้เวกเตอร์ใกล้กัน ใช้ใน semantic search, จับประโยคซ้ำ (เช่น Quora), clustering, recommendation และ RAG

**คุณสมบัติที่ต้องการ (สไลด์ 3):** `sim(f(s1), f(s2)) ≈ semantic_similarity(s1, s2)` คือความคล้ายของเวกเตอร์ต้องเดินตามความคล้ายของความหมาย และ f ต้องแปลงข้อความความยาวไม่คงที่ให้เป็นเวกเตอร์หนาแน่นขนาดคงที่ งานทั้งห้า (semantic search ที่ไม่ใช่แค่จับ keyword, duplicate detection, clustering ข่าวหรือข้อร้องเรียน, recommendation, RAG) ต้องการฟังก์ชันเดียวกันนี้

**ทบทวนจากสัปดาห์ 8 (สไลด์ 2):** สามกระบวนทัศน์คือ (1) Encoder เช่น BERT สองทิศทาง ใช้ classification, NER, QA (2) Decoder เช่น GPT แบบ causal ใช้ generation, ICL (3) Encoder-Decoder เช่น T5/BART ใช้ seq2seq, แปล, สรุป สัปดาห์ 9 ต่อยอดกระบวนทัศน์ที่ 1 ไปสู่ภารกิจใหม่คือ representation และ retrieval ช่องว่างที่ต้องปิดคือ สัปดาห์ 6 สอน BERT ทำ classification ผ่าน `[CLS]` กับ linear head แต่ถ้าต้อง **เปรียบเทียบสองประโยค** หรือ **ค้นหาประโยคคล้าย** ต้องมีเวกเตอร์ประโยคขนาดคงที่คุณภาพสูง ซึ่ง BERT ดิบทำได้ไม่ดี

วิธีง่าย ๆ สองแบบคือเฉลี่ยเวกเตอร์ทุก token (mean pooling) หรือใช้ `[CLS]` ตรง ๆ ผลบน STS benchmark (Spearman ρ, จาก SBERT paper):

| วิธี | คะแนน |
|---|---|
| GloVe average | 58.02 |
| BERT `[CLS]` (ไม่ fine-tune) | **16.50** |
| BERT mean pooling (ไม่ fine-tune) | 46.35 |
| SBERT-NLI-base | **77.03** |

BERT ดิบแพ้แม้แต่ GloVe เฉลี่ย `[CLS]` เทรนมาเพื่อ NSP (Next Sentence Prediction) ไม่ได้เทรนเพื่อความหมายของประโยค

**ตัวอย่าง: mean pooling ทีละขั้น (ตัวเลขสมมติ ใช้ 2 มิติแทน 768 มิติ)**

ประโยค "ฉันกินข้าว" แบ่งเป็น 3 token และ BERT ให้เวกเตอร์ของแต่ละ token ดังนี้

| token | เวกเตอร์ (สมมติ) |
|---|---|
| ฉัน | [1, 0] |
| กิน | [3, 2] |
| ข้าว | [5, 4] |

1. รวมมิติแรก: 1 + 3 + 5 = 9 และมิติสอง: 0 + 2 + 4 = 6
2. หารด้วยจำนวน token (3): [9/3, 6/3] = [3, 2]
3. [3, 2] คือเวกเตอร์ของทั้งประโยค ส่วนวิธี `[CLS]` จะหยิบเวกเตอร์ตำแหน่งแรกมาใช้เลยโดยไม่เฉลี่ย

**อธิบายละเอียดว่าสองวิธีทำอะไร (สไลด์ 4)**

- BERT ให้เวกเตอร์ contextual ของทุก token: `H = BERT(tokens) ∈ ℝ[B, T, d]` โดย B คือจำนวนประโยคใน batch, T คือความยาวลำดับ (นับ `[CLS]`, `[SEP]`, `[PAD]` ด้วย) และ d = 768 สำหรับ BERT-base
- วิธีที่ 1 mean pooling: `s = (1/T) Σₜ Hₜ ∈ ℝ^d` สไลด์ 4 เฉลี่ยทุกตำแหน่ง ส่วนสไลด์ 15 ปรับให้ใช้ mask ตัด `[PAD]`
- วิธีที่ 2 `[CLS]`: `s = H₀ ∈ ℝ^d` คือเวกเตอร์ของ token ตำแหน่งแรก
- ความหวังที่สไลด์ตั้งไว้: เวกเตอร์ลึกและมีบริบทมาก เฉลี่ยแล้วน่าจะเป็นตัวแทนประโยคได้ แต่ผลจริงคือทั้งสองวิธีแพ้ GloVe average
- ช่องว่างของคะแนน (คำนวณเอง): `[CLS]` ต่ำกว่า GloVe 41.52 จุด (58.02 − 16.50), mean pooling ต่ำกว่า GloVe 11.67 จุด (58.02 − 46.35), SBERT-NLI สูงกว่า mean pooling 30.68 จุด (77.03 − 46.35) และสูงกว่า GloVe 19.01 จุด (77.03 − 58.02)

**ตัวเลขที่ชวนสับสน (ใช้ให้ถูกบริบท)**

- GloVe และ BERT mean มีสองรูป คือ 58.02 และ 46.35 (สไลด์ 4) กับ 58.2 และ 46.4 (สไลด์ 19) เป็นการปัดเศษของค่าเดียวกัน
- SBERT-base มีสองค่า คือ 77.03 (STS Benchmark, สไลด์ 4 และ 19) กับ 74.89 (สไลด์ 24 ตารางเทียบกับ SimCSE) ผมไม่ได้ตรวจว่าสองค่านี้วัดแบบเดียวกันหรือไม่ จึงอย่านำมาลบกัน
- สัปดาห์ 6 ใช้ `[CLS]` กับ linear head เพื่อ classify ประโยคเดี่ยว ส่วนสัปดาห์ 9 ใช้เวกเตอร์คู่ `[u; v; |u−v|]`

## 2. สาเหตุ: Anisotropy (สไลด์ 5-6, 11-12)

> **พูดง่าย ๆ:** ถ้าร้านอาหารทั้งประเทศไปตั้งอยู่ในซอยเดียวกัน ร้านไหนก็ "อยู่ใกล้กันหมด" จึงบอกไม่ได้ว่าร้านไหนใกล้ความต้องการจริง BERT ดิบเป็นแบบนั้น เวกเตอร์ทุกตัวกระจุกอยู่ทิศเดียว

**ศัพท์ก่อนอ่าน:**

- anisotropy (เวกเตอร์กระจุกอยู่ในบางทิศ ไม่กระจายทั่ว) ส่วน isotropic คือกระจายสม่ำเสมอ
- cosine (ค่าวัดความคล้ายจากมุมระหว่างเวกเตอร์ ยิ่งใกล้ 1 ยิ่งชี้ทิศเดียวกัน)
- threshold (เกณฑ์ตัดสิน เช่น cosine เกินเท่านี้ถือว่าซ้ำ)
- MLM (Masked Language Modeling การปิดบางคำแล้วให้โมเดลทาย) และ NSP (ทายว่าประโยคสองสามารถต่อกันได้ไหม)
- hypersphere (ผิวทรงกลมในหลายมิติ ที่เวกเตอร์ความยาว 1 ทุกตัวอยู่บนนั้น)

เวกเตอร์ของ BERT ไม่กระจายสม่ำเสมอทุกทิศ แต่แออัดอยู่ใน **กรวยแคบ** ๆ

- cosine ของคู่ประโยคใด ๆ สูงหมด คู่ไม่เกี่ยวกันก็ได้คะแนนสูงเหมือนคู่ที่เกี่ยวกัน ไม่เหลือที่ว่างให้จัดอันดับ
- สไลด์ 12: `[CLS]` ดิบให้ 0.86 กับคู่ที่ไม่เกี่ยวกัน แต่ 0.79 กับคู่ที่เกี่ยวกัน คือ **อันดับกลับด้าน**
- ก่อน SBERT cosine อยู่ในช่วงประมาณ [0.46, 0.85] เฉลี่ย 0.58 หลัง SBERT เป็น [0.1, 0.99]
- Ethayarajh 2019: ชั้นลึกยิ่ง anisotropic มากขึ้น (ยกเว้นบางชั้น เช่น penultimate layer ของ BERT ที่สูงกว่าชั้นสุดท้าย)
- Mu & Viswanath: มีไม่กี่มิติที่สัมพันธ์กับความถี่ของคำ (เช่น "the", "a", "is") ดึงทุกเวกเตอร์ไปทิศเดียวกัน
- mean pooling สืบทอดปัญหานี้ และ `[CLS]` เทรนด้วย NSP จึงยิ่งไม่เหมาะ

**ตัวอย่างสไลด์ 11 (กิจกรรม):** s1=[0.91,0.38,0.15] แทน "The cat sat on the mat.", s2=[0.89,0.41,0.19] แทน "I love machine learning.", s3=[0.90,0.39,0.17] แทน "Dogs chase cats in the park." โจทย์ให้คำนวณ cos(s1,s2), cos(s1,s3), cos(s2,s3) คำนวณได้ cos(s1,s2) ≈ 0.9985, cos(s1,s3) ≈ 0.9997, cos(s2,s3) ≈ 0.9996 ทั้งที่เป็นประโยคคนละเรื่อง เห็นชัดว่าเวกเตอร์ในกรวยแคบทำให้ cosine แยกไม่ออก

**ตัวอย่าง: เกณฑ์ตัดสินพังเพราะกรวยแคบ (ตัวเลขสมมติ)** สมมติมี 4 คู่ประโยค และตั้งกฎว่า "cosine ≥ 0.50 คือประโยคซ้ำ"

| คู่ประโยค | ซ้ำจริงไหม | cosine จาก BERT ดิบ | cosine จาก SBERT |
|---|---|---|---|
| A กับ A' (เรื่องเดียวกัน) | ใช่ | 0.78 | 0.85 |
| A กับ B (คนละเรื่อง) | ไม่ | 0.62 | 0.08 |
| A กับ C (คนละเรื่อง) | ไม่ | 0.55 | −0.05 |
| B กับ C (คนละเรื่อง) | ไม่ | 0.60 | 0.12 |

- BERT ดิบ: ทั้ง 4 คู่ผ่านเกณฑ์ 0.50 ถูกตัดสินว่าซ้ำหมด ถูกแค่ 1 จาก 4 คู่ เพราะค่าต่ำสุดยังสูงอยู่
- SBERT: มีคู่เดียวที่ผ่านเกณฑ์ ถูกทั้ง 4 คู่ เพราะค่าที่ต่างกันกระจายได้กว้าง

**ต้องจำ:** ปัญหาไม่ใช่สถาปัตยกรรม BERT แต่คือ **training objective** (MLM) ที่ไม่เคยบังคับให้เรขาคณิตระดับประโยคดี

**นิยามและวิธีวัด**

- Isotropic คือเวกเตอร์กระจายสม่ำเสมอทุกทิศ ค่า cosine เฉลี่ยของเวกเตอร์สุ่มสองตัวจึงควรใกล้ 0 ส่วน anisotropic คือกระจุกอยู่ในบางทิศ ค่า cosine เฉลี่ยจึงไม่เป็น 0
- วิธีวัดที่ใช้ในสไลด์และเดโมคือดู **ค่าเฉลี่ย และโดยเฉพาะค่าต่ำสุด** ของ cosine ทุกคู่ (n ประโยคมี n(n−1)/2 คู่) ถ้าค่าต่ำสุดยังสูง แปลว่าไม่มีคู่ไหนถูกมองว่า "ไม่เหมือนกัน"
- narrow cone ไม่ได้แปลว่า "ทุกคู่ได้ 0.99" แต่แปลว่า "ไม่มีคู่ไหนได้ค่าต่ำ" จึงไม่เหลือช่วงให้จัดอันดับ ตัวเลขสไลด์ 19 คือ raw BERT อยู่ใน [0.46, 0.85] เฉลี่ย 0.58 ส่วน SBERT อยู่ใน [0.1, 0.99]

**ผลเสียเชิงปฏิบัติ**

- threshold ใช้ไม่ได้: ถ้าตั้งกฎ "cosine ≥ 0.40 คือประโยคซ้ำ" กับ raw BERT ที่ต่ำสุดประมาณ 0.46 ทุกคู่จะถูกตัดสินว่าซ้ำ
- ranking กลับด้านได้: เดโมสไลด์ 12 ให้ `[CLS]` ดิบของคู่ที่ไม่เกี่ยวกัน 0.86 สูงกว่าคู่ที่เกี่ยวกัน 0.79
- ชั้นลึกยิ่งแย่: สไลด์ 5 (จากเปเปอร์ Ethayarajh) บอกว่าชั้นสูงมักมี anisotropy มากกว่าชั้นล่าง ข้อยกเว้นคือ input layer ของ ELMo และ penultimate layer ของ BERT ที่ anisotropic กว่าชั้นสุดท้าย
- วิธีอ่านกราฟสไลด์ 5 (Ethayarajh 2019): แกน x คือเลขชั้น (layer index 0-12) แกน y คือ **ค่า cosine เฉลี่ยของคำที่สุ่มจากคนละตำแหน่ง** ถ้าเวกเตอร์กระจายสม่ำเสมอทุกทิศ (isotropic) เส้นควรอยู่ใกล้ 0 ค่าที่ไม่เป็น 0 จึงหมายถึง anisotropy ค่าที่อ่านได้คร่าว ๆ จากกราฟ (อ่านด้วยตา ไม่ใช่ตัวเลขจากข้อความ): BERT เริ่มราว 0.1 ที่ชั้น 0 แล้วค่อย ๆ สูงขึ้นถึงราว 0.67 ที่ชั้น 11 และตกลงราว 0.46 ที่ชั้น 12 ส่วน GPT-2 อยู่ราว 0.6 ตลอดและพุ่งใกล้ 1 ที่ชั้นสุดท้าย ส่วน ELMo ชั้นอินพุตต่ำสุดราว 0.02 เพราะใช้เวกเตอร์ระดับตัวอักษรที่ไม่มีบริบท ข้อสรุปที่ข้อสอบถามได้คือ **ยิ่งชั้นลึก ยิ่ง anisotropic** (ข้อยกเว้นคือ BERT ชั้นรองสุดท้าย) และไม่มีโมเดลใดใน BERT, ELMo, GPT-2 ที่เป็น isotropic จริง ยกเว้นชั้นอินพุตของ ELMo

**ทำไมสาเหตุคือ objective ไม่ใช่สถาปัตยกรรม**

- MLM ถามแค่ว่า token ที่ถูก mask คือคำไหน จึงฝึกให้ representation ของ *token* ดี แต่ไม่เคยมีสัญญาณที่บอกว่าประโยคสองประโยคควรอยู่ใกล้หรือไกลกัน
- สถาปัตยกรรม BERT ตัวเดิมเมื่อเปลี่ยน objective เป็น contrastive ก็สร้าง geometry ที่ดีได้ (SBERT) จึงสรุปได้ว่าไม่ใช่ปัญหาที่สถาปัตยกรรม มิติ 768 หรือปริมาณข้อมูล
- ตัวเลือกหลอกที่พบในชุดฝึกซ้อม: "มิติเล็กเกินไป", "ข้อมูล pre-train น้อยเกินไป", "self-attention สร้างเวกเตอร์ประโยคไม่ได้" ทั้งหมดผิดตามสไลด์ 9 และ 47

{{fig:week09-anisotropy-cone | เวกเตอร์ของ BERT ดิบอยู่รวมในกรวยแคบจน cosine ทุกคู่สูงหมด หลัง fine-tune แบบ SBERT เวกเตอร์กระจายทั่ว hypersphere จัดอันดับได้}}

**แก้ได้ 3 ทาง (สไลด์ 9)**

| แนวทาง | วิธี | คุณภาพ | สถานะ |
|---|---|---|---|
| 1. Post-processing | ลบมิติที่ครอบงำ (all-but-the-top, whitening) | ดีขึ้นปานกลาง | แค่ผ้าพันแผล |
| 2. Contrastive fine-tuning | Siamese/Dual-Encoder + contrastive loss | สูง | มาตรฐานอุตสาหกรรม (SBERT) |
| 3. Unsupervised contrastive | SimCSE ใช้ dropout เป็น augmentation | ดี ไม่ต้องใช้ label | baseline แข็ง |

สไลด์ 9 สรุปว่าปัญหาไม่ได้อยู่ที่สถาปัตยกรรมของ BERT แต่อยู่ที่ objective จึงต้อง **เทรนด้วย loss ที่ปรับ geometry ของประโยคโดยตรง** วิธีที่ 1 แก้เฉพาะอาการ (ลบทิศที่ครอบงำ) โดยไม่ได้สอนอะไรใหม่ให้โมเดล จึงเป็นเพียง "ผ้าพันแผล" ส่วนวิธีที่ 2 และ 3 ปรับน้ำหนักของโมเดลจริงด้วย contrastive loss ความต่างระหว่างสองวิธีหลังคือ วิธีที่ 2 ใช้ข้อมูลคู่ที่มี label (NLI/STS) วิธีที่ 3 ไม่ใช้ label

## 3. Cosine, L2, Dot Product (สไลด์ 10)

> **พูดง่าย ๆ:** เวกเตอร์เหมือนลูกศร cosine ดูแค่ว่าลูกศรชี้ไปทางเดียวกันไหม ไม่สนว่ายาวแค่ไหน ส่วน dot product และ L2 สนความยาวด้วย การ normalize คือตัดลูกศรทุกอันให้ยาว 1 เท่ากัน แล้วทั้งสามวิธีจะเรียงอันดับตรงกัน

**ศัพท์ก่อนอ่าน:**

- dot product (ผลคูณจุด คือคูณทีละมิติแล้วบวกกัน)
- L2 distance (ระยะห่างแบบไม้บรรทัด ระหว่างปลายลูกศรสองอัน)
- normalize หรือ L2-normalize (หารเวกเตอร์ด้วยความยาวของตัวเอง ให้ความยาวเป็น 1)
- orthogonal (ตั้งฉากกัน)

- `cos(u,v) = u·v / (‖u‖‖v‖)` อยู่ในช่วง [−1, 1] โดย 1 = ทิศเดียวกัน (identical direction), 0 = ตั้งฉาก (orthogonal), −1 = ทิศตรงข้าม (opposite)
- Cosine distance = `1 − cos` อยู่ในช่วง [0, 2]
- L2 distance = `‖u−v‖₂ = sqrt(Σ(uᵢ−vᵢ)²)`
- `u·v = ‖u‖‖v‖cos(u,v)`
- **ถ้า L2-normalize แล้ว** dot product = cosine และทั้งสามตัวชี้วัดให้ **อันดับเท่ากัน** นี่คือเหตุผลที่ต้อง normalize ถ้าไม่ normalize การค้นหาจะถูกครอบงำด้วยขนาดเวกเตอร์ ไม่ใช่ความหมาย

**ที่มาทางคณิตศาสตร์ว่าทำไม normalize แล้วอันดับเท่ากัน (ความรู้ทั่วไป ไม่ใช่สไลด์)** ถ้า ‖u‖ = ‖v‖ = 1 แล้ว ‖u−v‖² = ‖u‖² + ‖v‖² − 2u·v = 2 − 2cos(u,v) ดังนั้นระยะ L2 ยิ่งน้อย cosine ยิ่งมาก (เรียงกลับกันอย่างสม่ำเสมอ) และ dot product ก็เท่ากับ cosine อยู่แล้ว ตัวอย่าง cos = 0.96 ได้ ‖u−v‖² = 2 − 2 × 0.96 = 0.08

**ตัวอย่างที่ไม่ได้ normalize (คำนวณเอง)** q = [3, 4], d₁ = [1.5, 2] (ทิศเดียวกับ q แต่สั้นครึ่งหนึ่ง), d₂ = [4, 3]

| metric | d₁ | d₂ | อันดับ 1 |
|---|---|---|---|
| cosine | 1.0000 | 0.9600 | d₁ |
| dot product | 12.5 | 24 | d₂ |
| L2 distance | 2.5 | 1.4142 | d₂ |

**คำนวณทีละขั้นของ d₂ = [4, 3] (ตัวอย่างข้างบน):**

1. dot = 3×4 + 4×3 = 12 + 12 = 24
2. ความยาว q = sqrt(3² + 4²) = 5 และความยาว d₂ = sqrt(4² + 3²) = 5
3. cosine = 24 / (5 × 5) = 0.96
4. L2 = sqrt((3−4)² + (4−3)²) = sqrt(2) = 1.4142

สามเมตริกให้อันดับต่างกัน เพราะ dot และ L2 ถูกขนาดเวกเตอร์ครอบงำ อีกตัวอย่างคือ u = [3, 4] กับ v = [6, 8] ชี้ทิศเดียวกัน (cos = 1) แต่ dot = 50 และ L2 = 5 ไม่ใช่ 0 นี่คือเหตุผลที่สไลด์ 42 เตือนว่าความผิดพลาดที่พบบ่อยคือใช้ L2 กับเวกเตอร์ที่ไม่ได้ normalize

## 4. Cross-Encoder เทียบกับ Bi-Encoder (สไลด์ 7-8, 18)

> **พูดง่าย ๆ:** Cross-encoder เหมือนกรรมการที่อ่านทีละคู่อย่างละเอียด แม่นแต่ช้า Bi-encoder เหมือนทำบัตรประจำตัว (เวกเตอร์) ให้ทุกคนครั้งเดียว แล้วเทียบบัตรได้เร็วมาก เลยใช้ bi-encoder คัดรอบแรก แล้วให้ cross-encoder ตัดสินรอบสอง

**ศัพท์ก่อนอ่าน:**

- forward pass (การส่งข้อมูลผ่านโมเดลหนึ่งรอบเพื่อให้ได้ผลลัพธ์ ใช้เวลาระดับมิลลิวินาที)
- cross-attention (ให้ token ของประโยค A มองดู token ของประโยค B ได้โดยตรง)
- O(n²) (ต้นทุนโตเป็นกำลังสองของ n เช่น n เพิ่ม 10 เท่า งานเพิ่ม 100 เท่า)
- top-k (k อันดับแรกที่คะแนนสูงสุด)
- rerank (จัดอันดับรายการที่ดึงมาแล้วใหม่)
- recall และ precision (ครอบคลุมแค่ไหน และตรงเป้าแค่ไหน ดูหัวข้อ 11)

**Cross-Encoder:** ต่อประโยคเป็น `[CLS] A [SEP] B [SEP]` ผ่าน BERT แล้วใช้ `[CLS]` ไปเข้า head ให้คะแนน คุณภาพยอดเยี่ยมเพราะมี cross-attention เต็มระหว่าง A กับ B แต่ต้องรันหนึ่ง forward pass ต่อหนึ่งคู่ จำนวนคู่ของ n ประโยคคือ n(n−1)/2

**Bi-Encoder:** encode แต่ละประโยคแยกกัน `s_A = f(A)`, `s_B = f(B)` แล้วเทียบด้วย `cos(s_A, s_B)` ใช้ n forward pass บวก dot product ที่เร็วมาก

**ความซับซ้อนสองระดับที่สไลด์ 7-8 ระบุ (ต้องแยกให้ออก)**

- ต่อหนึ่งคู่ของ cross-encoder ต้นทุนคือ `O(L²)` เมื่อ L = ความยาวรวมของลำดับที่ต่อกัน (`[CLS] A [SEP] B [SEP]`) เพราะ self-attention เทียบทุก token กับทุก token ในลำดับที่ต่อกันนั้น
- ต่อทั้งชุด n ประโยค ต้องรัน forward pass `n(n−1)/2` ครั้ง (นี่คือจำนวนครั้งที่ต้องรัน BERT) สองตัวเลขนี้ซ้อนกัน: ต้นทุนรวมของ cross-encoder = จำนวนคู่ × ต้นทุนต่อคู่ที่เป็น O(L²)
- ฝั่ง bi-encoder: n forward pass (แต่ละครั้ง encode ประโยคเดียว) บวก `O(n²·d)` dot product (สไลด์ 8 และ 18) ที่แต่ละครั้งเป็นการคูณบวก d ค่า จึงเร็วมากเมื่อเทียบกับ forward pass ของ BERT

**ตัวเลขตัวอย่าง (n = 10,000 ประโยค, 5ms ต่อ forward)**

- Cross-encoder ต้อง ≈ 50 ล้านคู่ ≈ **69 ชั่วโมง**
- Bi-encoder ใช้ 10,000 forward ≈ **50 วินาที** แล้วเทียบทุกคู่ไม่ถึง 1 วินาที

| | Bi-Encoder (SBERT) | Cross-Encoder |
|---|---|---|
| อินพุต | encode แต่ละประโยคแยกกัน | ต่อประโยคเป็น `[CLS] A [SEP] B [SEP]` |
| โครงสร้าง | BERT สองหอ → pool → เทียบเวกเตอร์ | BERT เดียว → `[CLS]` → คะแนน |
| Cross-sentence attention | ไม่มี | มีเต็มที่ |
| เอาต์พุต | เวกเตอร์ u, v → similarity | คะแนนเดียว |
| คุณภาพ | ดี | ยอดเยี่ยม |
| ความเร็ว | O(n) forward + O(n²·d) dot product | O(n²) forward |
| Pre-compute | ได้ (cache เวกเตอร์) | ไม่ได้ ต้องรันทุกคู่ |
| ใช้ทำอะไร | ดึงผู้สมัครรอบแรก (recall) | จัดอันดับรอบสอง (precision) |

{{fig:week09-bi-vs-cross | Bi-Encoder encode แต่ละประโยคแยกกันแล้วเทียบเวกเตอร์ (n forward pass) ส่วน Cross-Encoder ต้องรัน BERT ใหม่ทุกคู่ (n² forward pass)}}

**ตัวอย่าง: ค้นหนึ่ง query ในคลังแนวทางการรักษา (ตัวเลขสมมติ)** สมมติมี 2,000 ชิ้นข้อความ (chunk) และ forward pass หนึ่งครั้งใช้ 20 ms บน CPU

| วิธี | งานต่อ 1 query | เวลา |
|---|---|---|
| Cross-encoder จับคู่กับทุก chunk | 2,000 forward | 2,000 × 20 ms = 40,000 ms = 40 วินาที |
| Bi-encoder (เวกเตอร์ของ chunk เก็บไว้แล้ว) | 1 forward ของ query แล้วคูณ dot 2,000 ครั้ง | ≈ 20 ms บวกเวลา dot product ที่น้อยมาก |
| Bi-encoder ดึง top-20 แล้ว cross-encoder จัดอันดับใหม่ | 1 + 20 forward | 20 + 20 × 20 = 420 ms |

- การสร้างเวกเตอร์ของ chunk ทั้ง 2,000 ชิ้นครั้งแรกใช้ 2,000 × 20 ms = 40 วินาที แต่ทำครั้งเดียวแบบออฟไลน์ แล้วเก็บไว้ใช้ซ้ำ
- บทเรียน: การจัดอันดับใหม่เฉพาะ top-20 ทำให้ได้ความแม่นของ cross-encoder โดยไม่ต้องจ่ายค่า 40 วินาทีต่อ query

**Pipeline Retrieve-then-Rerank:** Bi-Encoder ดึง top-k จากหลายล้านเอกสาร แล้ว Cross-Encoder จัดอันดับ top-k ใหม่ (พรีวิวสัปดาห์ 12)

**O( ) ในตารางนี้นับอะไร (อาจารย์เน้น)**

- Cross-encoder: O(n²) นับ **จำนวนครั้งของ forward pass ของ BERT** ซึ่งแต่ละครั้งใช้เวลาระดับมิลลิวินาที ถ้าไม่นับคู่ซ้ำและไม่จับคู่กับตัวเอง จำนวนคู่ที่แน่นอนคือ n(n−1)/2 (สไลด์ 7 ใช้สูตรนี้ 10,000 × 9,999 / 2 ≈ 50 ล้าน) ส่วน n² เป็นลำดับขนาดของการเติบโต
- Bi-encoder: n forward pass (ระดับ ms ต่อครั้ง) บวก dot product ราว n² ครั้ง ซึ่งแต่ละครั้งใช้เวลาระดับนาโนวินาที จึงถูกกว่ามาก
- ตัวหลอก: "Bi-encoder ไม่ต้อง forward เลยเพราะ cache" ผิด ต้อง forward n ครั้งเพื่อสร้างเวกเตอร์ครั้งแรก แล้ว cache ได้ถ้าข้อความและโมเดลไม่เปลี่ยน

**เลข 50 วินาที เทียบกับ 5 วินาที:** สไลด์ 8 ระบุ bi-encoder ราว 50 วินาที (10,000 × 5 ms) ส่วนบทคัดย่อ SBERT ระบุราว 5 วินาทีและ 65 ชั่วโมง และ hint จากการถอดเสียงของอาจารย์พูดถึง ~5 วินาที สามแหล่งนี้ตัวเลขต่างกัน ผมไม่ได้ตรวจว่าเพราะอะไร ถ้าโจทย์ให้เวลาต่อ forward มา ให้คำนวณจากที่โจทย์ให้ ถ้าถามตามสไลด์ใช้ 50 วินาทีและ 69 ชั่วโมง

**ต้นทุนรวมของ Retrieve-then-Rerank:** เวลาต่อ query = เวลา encode query + เวลาค้น FAISS + (k × เวลา cross-encoder ต่อคู่) โดยเวกเตอร์เอกสารถูก encode ไว้ล่วงหน้าแล้ว ตัวอย่างที่คำนวณเต็มอยู่ในส่วนโจทย์คำนวณท้ายบทเรียน

## 5. Siamese Network และ SBERT (สไลด์ 13-17, 20-23)

> **พูดง่าย ๆ:** Siamese คือแฝดสองคนที่ใช้สมองเดียวกัน อ่านประโยคละคนแล้วเทียบคำตอบกัน SBERT คือการเอา BERT มาฝึกต่อด้วยวิธีนี้ จนกลายเป็นเครื่องสร้างพิกัดความหมายที่ใช้ได้จริง

**ศัพท์ก่อนอ่าน:**

- weight sharing (สองสาขาใช้น้ำหนักชุดเดียวกัน และปรับพร้อมกัน)
- fine-tune (ฝึกโมเดลที่เทรนมาแล้วต่ออีกนิดด้วยข้อมูลของงานเรา)
- logits (คะแนนดิบของแต่ละ label ก่อนผ่าน softmax)
- softmax cross-entropy (loss สำหรับจำแนกประเภท ยิ่งให้ความน่าจะเป็นกับคำตอบถูกมาก loss ยิ่งต่ำ)
- MSE (Mean Squared Error ค่าเฉลี่ยของผลต่างยกกำลังสอง)
- NLI (Natural Language Inference ชุดข้อมูลคู่ประโยคที่มี label ว่าประโยคหนึ่งสนับสนุน ขัดแย้ง หรือไม่เกี่ยวกับอีกประโยค)
- attention mask (ตัวบอกว่า token ไหนจริง ไหนเป็น `[PAD]`)
- `[PAD]` (token เติมให้ทุกประโยคใน batch ยาวเท่ากัน)

**Siamese (Bromley 1993, Chopra 2005):** สองสาขาที่ใช้ **สถาปัตยกรรมเดียวกันและน้ำหนักเดียวกัน (weight sharing)** อัปเดตพร้อมกัน ใช้ฟังก์ชัน `f_θ` เดียวกับทั้งสองอินพุต: `e_A = f_θ(x_A)`, `e_B = f_θ(x_B)` แล้ววัดความคล้ายด้วย `sim(e_A, e_B) = cos(e_A, e_B)` หรือใช้ระยะ `‖e_A − e_B‖` (สไลด์ 13) จุดสำคัญคือ **ฟังก์ชัน f เดียวกันกับทั้งสองอินพุต** และเมื่ออัปเดตน้ำหนักทั้งสองสาขาเปลี่ยนเหมือนกันเสมอ เป้าหมายคือฉายอินพุตทั้งสองลงปริภูมิร่วมที่ระยะหรือความคล้ายมีความหมายเชิงความหมาย ต้นกำเนิดมาจากการตรวจสอบลายเซ็น ต่อมาใช้กับ face recognition (FaceNet) และ one-shot learning

**SBERT (Reimers & Gurevych 2019)** = BERT ที่ pre-train แล้ว + pooling + fine-tune แบบ Siamese ด้วยข้อมูลคู่ประโยค ประกอบด้วย (1) shared BERT encoder (2) pooling layer (3) ฟังก์ชัน similarity/loss ใช้เวลา fine-tune ไม่ถึง 20 นาที

**Pooling 3 แบบ**

| แบบ | ทำอะไร | หมายเหตุ |
|---|---|---|
| CLS | `s = H₀` | เทรนมาจาก NSP ซึ่งเป็นสัญญาณที่แย่ (RoBERTa ablation ยืนยัน) |
| **Mean** (ค่าเริ่มต้น) | `s = Σ Hₜ·mₜ / Σ mₜ` โดย `mₜ∈{0,1}` คือ attention mask | ผลดีที่สุด |
| Max | `sᵢ = maxₜ Hₜ,ᵢ` | จับค่าสูงสุดต่อมิติ แต่เสียภาพรวมการกระจาย |

ต้องใช้ attention mask เพื่อไม่ให้ `[PAD]` ปนในค่าเฉลี่ย

**ผล ablation ของ pooling (สไลด์ 15, Table 6 ของ SBERT, Spearman ρ)**

| Pooling | ฝึกด้วย NLI (classification) | ฝึกด้วย STSb (regression) |
|---|---|---|
| Mean | 80.78 | 87.44 |
| CLS | 79.80 | 86.62 |
| Max | 79.07 | 69.92 |

- Mean ชนะทั้งสองการฝึก: เหนือ CLS 0.98 จุดเมื่อฝึกด้วย NLI และ 0.82 จุดเมื่อฝึกด้วย STSb
- Max ตกหนักเมื่อฝึกด้วย STSb (69.92) ซึ่งตรงกับที่สไลด์บอกว่า max จับค่าสูงสุดต่อมิติแต่เสียภาพรวมของการกระจาย
- ตัวเลขนี้เป็นของโมเดลที่ **ผ่านการฝึกแบบ SBERT แล้ว** ไม่ใช่ BERT ดิบ (BERT ดิบอยู่ในตารางสไลด์ 4)

**ทำไมต้องใช้ mask:** ประโยคใน batch ยาวไม่เท่ากัน จึงต้องเติม `[PAD]` ให้เท่ากัน mask `mₜ` เป็น 1 สำหรับ token จริงและ 0 สำหรับ `[PAD]` ของ **แต่ละประโยค** ตัวหารจึงเป็น Σ mₜ (จำนวน token จริง) ไม่ใช่ T ถ้าไม่ใช้ mask เวกเตอร์ของ `[PAD]` จะปนเข้าไปในค่าเฉลี่ยและบิดเบือนเวกเตอร์ประโยค (ตัวอย่างตัวเลขอยู่ในส่วนโจทย์คำนวณ และเดโมวัดว่าเวกเตอร์ `[PAD]` ไม่ได้เล็กใกล้ศูนย์)

**ตัวอย่าง: masked mean pooling ทีละขั้น (ตัวเลขสมมติ 2 มิติ)** ประโยคหนึ่งมี token จริง 4 ตัว และถูกเติม `[PAD]` อีก 2 ตัวให้ยาวเท่าประโยคอื่นใน batch ตามเดโม เวกเตอร์ `[PAD]` ไม่ได้เป็นศูนย์ สมมติให้เป็น [9, 9]

| ตำแหน่ง | token | เวกเตอร์ | mask |
|---|---|---|---|
| 1 | token จริง | [2, 1] | 1 |
| 2 | token จริง | [4, 3] | 1 |
| 3 | token จริง | [6, 5] | 1 |
| 4 | token จริง | [0, 3] | 1 |
| 5 | `[PAD]` | [9, 9] | 0 |
| 6 | `[PAD]` | [9, 9] | 0 |

1. ใช้ mask: รวมเฉพาะ token จริงได้ [2+4+6+0, 1+3+5+3] = [12, 12] ตัวหารคือ Σ mask = 4 ได้ [3, 3]
2. ไม่ใช้ mask: รวมทั้ง 6 ตำแหน่งได้ [12+18, 12+18] = [30, 30] ตัวหารคือ 6 ได้ [5, 5]
3. เวกเตอร์ประโยคเพี้ยนจาก [3, 3] เป็น [5, 5] เพราะ `[PAD]` ปนเข้ามา ซึ่งเป็นเหตุผลที่ต้องใช้ mask

**3 โครงแบบการเทรนของ SBERT**

| Config | อินพุต | Loss | ข้อมูล |
|---|---|---|---|
| Classification | คู่ประโยค + label (entail / neutral / contradict) | softmax cross-entropy บน `[u; v; \|u−v\|]` | NLI |
| Regression | คู่ประโยค + คะแนน | MSE ระหว่าง `cos(u,v)` กับคะแนน | STS |
| Triplet | (anchor, positive, negative) | triplet margin loss | งาน retrieval |

รูปในสไลด์ 14 วาดสองโครงสร้าง ทั้งคู่ใช้ BERT สองหอที่น้ำหนักร่วมกัน (tied weights) → pooling → u, v **โครงบน (classification)** ต่อ `(u, v, |u−v|)` เข้า softmax classifier **โครงล่าง (regression)** ต่อ `cosine-sim(u, v)` ซึ่งอยู่ในช่วง −1 ถึง 1 ตัวอักษร ε ใน triplet ของเปเปอร์ SBERT คือ margin ตัวเดียวกับ α ในสไลด์ 27 (สไลด์ 27 และเดโมระบุว่าเปเปอร์ใช้ระยะ Euclidean และ ε = 1)

**Tensor walkthrough (classification, สไลด์ 17)**

- A = "A man is eating food" ได้ `input_ids [1,7]` และ B ได้ `[1,8]` (tokenize แยกกัน ความยาวต่างกันได้ และแต่ละประโยคมี `attention_mask` ของตัวเอง) หมายเหตุ: สไลด์ 17 สะกด B ว่า "A man is eating passta" ส่วนสไลด์ 22 สะกด pasta จำนวน token ขึ้นกับ tokenizer ให้ยึด shape ตามสไลด์ ([1,7] และ [1,8]) ไม่ต้องนับเอง
- BERT ที่ใช้น้ำหนักร่วม รันสองครั้ง ได้ `H_A ∈ [1,7,768]`, `H_B ∈ [1,8,768]`
- masked mean pooling ได้ `u, v ∈ [1,768]`
- concat `c = [u; v; |u−v|] ∈ [B, 2304]` (768×3)
- `W ∈ ℝ^(2304×3)` ได้ logits `[1,3]` แล้ว `CrossEntropy(logits, label)`

**หมายเหตุสำคัญของ forward pass นี้**

- มิติของ c เท่ากับ 3d เสมอ: d = 384 ได้ 1,152, d = 768 ได้ 2,304, d = 1024 ได้ 3,072 ตัวหลอก 1,536 คือกรณีต่อแค่ `[u; v]` (2 × 768) ซึ่งไม่ใช่ SBERT
- ขนาด `W` คือ (3d) × (จำนวน label): BERT-base ได้ 2,304 × 3 = 6,912 ตัว (บวก bias 3 ตัวเป็น 6,915 ตัว ซึ่งส่วน bias เป็นความรู้ทั่วไป ไม่ได้อยู่ในสไลด์) ถ้าเปลี่ยนเป็น d = 1024 ได้ 3,072 × 3 = 9,216 ตัว เพิ่มขึ้น 2,304 ตัว
- ใช้ `|u − v|` (ค่าสัมบูรณ์) ไม่ใช่ `u − v` เหตุผลที่ผมเข้าใจคือค่าสัมบูรณ์ไม่ขึ้นกับลำดับของสองประโยค ส่วนนี้เป็นความรู้ทั่วไป สไลด์เพียงระบุรูปแบบของ c
- classification head ใช้ตอน **เทรน** เท่านั้น ตอน inference (ตามรูป Figure 2 ในหน้าเปเปอร์ที่สไลด์ 14 แสดง) เทียบ u กับ v ด้วย cosine ตรง ๆ และโครงเดียวกันนี้ใช้กับ regression objective ด้วย
- เทียบกับสัปดาห์ 6: ใช้ฟังก์ชันของ head แบบเดิม (linear + softmax + cross-entropy) แต่อินพุตเป็นเวกเตอร์คู่ที่ประกอบจากสองประโยค ไม่ใช่ `[CLS]` ของประโยคเดียว (สไลด์ 22)

**NLI (สไลด์ 22):** SNLI (570K) + MultiNLI (430K) ≈ 1M คู่ ป้าย 3 แบบ

- "A man is eating pasta." + "A man is eating food." → Entailment (ดึงเข้าใกล้)
- "A man is eating pasta." + "A man is sleeping." → Contradiction (ผลักออก)
- "A man is eating pasta." + "The man is in Italy." → Neutral
- label ของ entailment/contradiction สอนเรขาคณิต "คล้าย→ใกล้, ต่าง→ไกล" ทางอ้อม โดยไม่ต้องมีคะแนน cosine เป้าหมาย เชื่อมกับสัปดาห์ 6 ตรงที่ใช้แนวคิด classification head เดิม แต่อินพุตเป็นเวกเตอร์คู่ ไม่ใช่ `[CLS]` เดี่ยว

**Regression (STSb, สไลด์ 23):** ~8,500 คู่ คะแนน 0-5 normalize เป็น [0,1] แล้ว MSE กับ `cos(u,v)` ตัวอย่าง "A plane is taking off." กับ "An air plane is taking off." ได้ 5.0 ส่วน "A man is playing a flute." กับ "A man is surfing." ได้ 0.0

**ทำไมต้อง normalize label เป็น [0,1] ก่อน:** `cos(u,v)` อยู่ใน [−1, 1] และไม่เกิน 1 ไม่ว่า u และ v จะยาวแค่ไหน ถ้าใช้ label 0-5 ตรง ๆ โมเดลจะไม่มีทางเข้าใกล้ label ที่มากกว่า 1 ได้ MSE จึงไม่ถึง 0 และโมเดลถูกดันให้ตั้ง cos = 1 กับทุกคู่ที่ label ≥ 1 จนแยกระดับความคล้ายไม่ได้ ถ้าหาร label ด้วย 5 เช่น 5.0 → 1.0, 4.0 → 0.8, 1.0 → 0.2, 0.0 → 0.0 โมเดลปรับ cos ให้เท่า label ได้ครบ (ตัวอย่างที่คำนวณ MSE ต่ำสุด 6.25 เทียบกับ 0 อยู่ในส่วนโจทย์คำนวณ)

**สูตรสองเฟสที่ดีที่สุด:** เฟส 1 เทรน NLI ด้วย classification (เรียนโครงหยาบ) เฟส 2 fine-tune บน STS ด้วย regression (ปรับความละเอียด)

**ลูปการเทรน (สไลด์ 33):** batch 16, lr 2×10⁻⁵ (Adam + warmup), 1 epoch, max seq 128, mean pooling ใช้ ~20 นาที (NLI) บวก ~5 นาที (STS) บน V100 ใบเดียว ต้อง backprop ผ่าน **BERT ทุกชั้น** ไม่ใช่แค่ pooling เพราะการปรับทุกชั้นคือสิ่งที่แก้ anisotropy สูตรสมัยใหม่ (2026) คือ AllNLI triplets + MNRL

**Alignment และ uniformity (Wang & Isola 2020, สไลด์ 19):** คุณภาพ embedding ดูจาก alignment (positive อยู่ใกล้กัน) และ uniformity (เวกเตอร์กระจายทั่ว hypersphere) กลไก "attract + repel" ของ contrastive loss ทำให้ใช้พื้นที่เชิงมุมทั้งหมด uniformity คือสิ่งตรงข้ามของ anisotropy ตัวเลข STS: GloVe 58.2 → BERT mean-pool 46.4 → SBERT 77.03

## 6. Contrastive Learning (สไลด์ 26-32)

> **พูดง่าย ๆ:** เหมือนจัดที่ยืนในห้อง ให้เพื่อนสนิทยืนติดกัน (ดึงเข้าหา) และคนแปลกหน้ายืนห่างกัน (ผลักออก) Triplet ใช้ตัวอย่างสามคน ส่วน MNRL ให้ทุกคนใน batch ช่วยเป็นคนแปลกหน้าฟรี ๆ

**ศัพท์ก่อนอ่าน:**

- anchor, positive, negative (ประโยคตั้งต้น, ประโยคที่ควรอยู่ใกล้, ประโยคที่ควรอยู่ไกล)
- margin α (ระยะห่างขั้นต่ำที่เราบังคับให้ negative ต้องไกลกว่า positive)
- gradient (ทิศทางและขนาดที่โมเดลใช้ปรับน้ำหนัก ถ้า loss เป็น 0 ก็ไม่มี gradient)
- batch (กลุ่มตัวอย่างที่ป้อนเข้าโมเดลพร้อมกันในหนึ่งรอบ) และ N คือขนาดของ batch
- softmax (แปลงคะแนนหลายตัวให้เป็นความน่าจะเป็นที่รวมกันได้ 1)
- τ หรือ temperature (ตัวหารที่ปรับว่า softmax จะคมหรือนุ่ม)
- hard negative (negative ที่ดูคล้าย anchor มากจนโมเดลสับสนง่าย)

หลักคิด: ดึง positive เข้าหากัน ผลัก negative ออก องค์ประกอบ 3 อย่างคือ anchor, positive, negative โดยเป้าหมายคือ `d(f(a), f(p)) ≪ d(f(a), f(n))` นี่คือ paradigm ไม่ใช่ loss ตัวเดียว

### Triplet Loss (Schroff et al. 2015)
`L = max(0, d(a,p) − d(a,n) + α)`

- α คือ margin (ปกติ 0.5-1.0) ถ้า `d(a,p) + α ≤ d(a,n)` แล้ว loss = 0 ไม่อัปเดต
- ถ้าไม่มี margin โมเดลจะ "ขี้เกียจ" พอแค่ห่างนิดเดียว margin ใหญ่ขึ้น geometry ดีขึ้นแต่เทรนยากขึ้น
- SBERT ใช้ระยะ Euclidean กับ ε = 1 ไลบรารีสมัยใหม่นิยม cosine distance
- เมื่อ L > 0 gradient ดึง p เข้าหา a และผลัก n ออก ถ้า L = 0 ตัวอย่างนั้นไม่มีผลต่อการอัปเดตเลย
- margin ทำให้ "ชนะ" อย่างเดียวไม่พอ ต้องชนะ **ด้วยระยะห่างอย่างน้อย α** ตัวอย่าง d(a,p) = 0.4, d(a,n) = 0.7, α = 0.5: positive ใกล้กว่าจริง แต่ห่างกันแค่ 0.3 ซึ่งน้อยกว่า 0.5 จึงยังมี loss = 0.4 − 0.7 + 0.5 = 0.2
- margin ที่ใหญ่เกินช่วงของ metric ทำให้ไม่มีวัน loss = 0: cosine distance อยู่ใน [0, 2] ถ้าใช้ α = 1.5 กับ cos(a,p) = 0.4 (d(a,p) = 0.6) ต้องมี d(a,n) ≥ 0.6 + 1.5 = 2.1 แต่ค่ามากสุดคือ 2 จึง loss ต่ำสุด = 0.1
- ตัวอย่างเดียวกันให้ loss ต่างกันเมื่อเปลี่ยน metric (cosine distance เทียบ Euclidean) ตัวเลขอยู่ในส่วนโจทย์คำนวณ นั่นคือ metric เป็นส่วนหนึ่งของ loss

**Hard negative mining**

| ชนิด | เงื่อนไข | ผล |
|---|---|---|
| Easy | `d(a,n) ≫ d(a,p)+α` | loss = 0 ไร้ประโยชน์ |
| Hard | `d(a,n) < d(a,p)` | gradient ใหญ่ แต่อาจทำให้เทรนไม่เสถียร |
| **Semi-hard** | `d(a,p) < d(a,n) < d(a,p)+α` | สมดุลที่สุด (ใช้ใน FaceNet) |

**ตัวอย่างเทียบสามชนิดด้วยเลข:** ให้ d(a,p) = 0.3 และ α = 0.5 ช่วง semi-hard คือ 0.3 < d(a,n) < 0.8

| d(a,n) | ชนิด | loss = 0.3 − d(a,n) + 0.5 |
|---|---|---|
| 0.2 | hard (ใกล้ anchor กว่า positive) | 0.6 |
| 0.5 | semi-hard | 0.3 |
| 0.9 | easy (≥ 0.8) | max(0, −0.1) = 0 |

ที่ขอบ d(a,n) = d(a,p) + α พอดี loss เป็น 0 (เงื่อนไข zero-loss ใช้ ≤) ส่วนนิยาม semi-hard ของสไลด์ใช้ < ซึ่งตัวอย่างข้อสอบไม่น่าชนขอบนี้

**ตัวอย่างคำนวณ (สไลด์ 32):** a=[0.3,0.7,0.1], p=[0.35,0.65,0.15], n=[0.8,0.2,0.5], α=0.5

- d(a,p) = sqrt(0.0075) ≈ 0.087 และ d(a,n) = sqrt(0.66) ≈ 0.812
- L = max(0, 0.087 − 0.812 + 0.5) = max(0, −0.225) = **0** negative ไกลพอแล้ว
- ถ้าใช้ hard negative n′=[0.32,0.68,0.12] ได้ d(a,n′) ≈ 0.035 → L = 0.087 − 0.035 + 0.5 = **0.552** เริ่มมี gradient

{{fig:week09-triplet-margin | ตัวอย่างสไลด์ 32 วาดตามสเกลบนแกนระยะห่างจาก anchor: negative ที่อยู่ไกลเกิน d(a,p)+α ได้ loss = 0 ส่วน negative ที่เข้ามาใกล้จึงมี gradient}}

### Margin Ranking Loss
`L = max(0, sim(a,n) − sim(a,p) + α)` ใช้ **similarity** แทน distance ถ้า `d = 1 − sim` จะเท่ากับ triplet loss (PyTorch: `MarginRankingLoss`)

**พิสูจน์ทีละขั้นว่าเท่ากัน:** แทน d = 1 − sim ในสูตร triplet จะได้ (1 − sim(a,p)) − (1 − sim(a,n)) + α = sim(a,n) − sim(a,p) + α เทอม 1 ตัดกันพอดี จึงได้สูตร margin ranking

- เท่ากันได้เฉพาะเมื่อใช้ **cosine distance** ถ้าเปลี่ยนเป็น Euclidean จะไม่เท่ากันอีก
- Triplet มองที่ระยะ (ต้องการ d(a,p) เล็ก d(a,n) ใหญ่) ส่วน margin ranking มองที่ความคล้าย (ต้องการ sim(a,p) สูง sim(a,n) ต่ำ) จึงลำดับเครื่องหมายสลับกัน
- กับดักที่พบบ่อยคือเขียนเครื่องหมายสลับ: a = [1,0], p = [0.8,0.6], n = [0,1] ที่ถูกคือ 0 − 0.8 + 0.5 = −0.3 ได้ loss 0 แต่ถ้าสลับเป็น 0.8 − 0 + 0.5 จะได้ 1.3 ซึ่งผิด

### MNRL / InfoNCE (แบบที่ใช้ในปัจจุบัน)
`Lᵢ = −log [ exp(sim(qᵢ,pᵢ)/τ) / Σⱼ exp(sim(qᵢ,pⱼ)/τ) ]`

- ใน batch ขนาด N เอาคู่ตัวอื่น (j≠i) เป็น negative ฟรี เช่น N=256 ได้ 255 negative โดยไม่ต้องขุดเอง
- τ (temperature) ปกติ 0.05-0.1: τ ต่ำ = ขอบตัดสินแข็งขึ้น, τ สูง = เรียนนุ่มลง
- ใช้ใน E5, BGE, GTE ข้อได้เปรียบคือข้อมูลต้องการแค่คู่ positive และขยายตาม batch size ได้
- อ่านสูตรเป็นภาษาคน: ใน batch มี N query และ N passage จึงคำนวณ similarity ได้ตาราง N × N แต่ละแถว i คือ softmax ที่ถามว่า "ใน p₁ ถึง p_N ตัวไหนเป็นคู่จริงของ qᵢ" และ loss คือ −log ของความน่าจะเป็นที่ให้ pᵢ (เทียบเท่า cross-entropy ที่เฉลยคือช่องแนวทแยง ซึ่งเป็นความรู้ทั่วไป)
- จำนวน negative ต่อ query คือ N − 1 (ไม่นับ pᵢ ของตัวเอง): N = 128 ได้ 127, N = 256 ได้ 255 (สไลด์ 30)
- batch ใหญ่ขึ้นได้ negative มากขึ้นโดยไม่ต้องสร้างข้อมูลเพิ่ม แต่ตาราง similarity โตเป็น N × N ต่อ step
- τ ต่ำ (0.1 เทียบกับ 1) ขยาย logit ทำให้ softmax คมขึ้น ตัวอย่างเลขสมมติ sim(q,p) = 0.8 และ negative = 0.2, 0.1: τ = 1 ได้ P(positive) = 0.4889 และ loss = 0.7156 ส่วน τ = 0.1 ได้ P = 0.9966 และ loss = 0.0034
- ตัวหลอก: "MNRL ต้องระบุ hard negative เอง" ผิด ต้องการแค่คู่ positive และ "τ สูงทำให้ขอบตัดสินแข็งกว่า" ผิด ต้องเป็น τ ต่ำ

{{fig:week09-mnrl-batch | MNRL ใช้ตารางความคล้ายขนาด N × N ของ batch: แนวทแยงคือ positive ส่วนช่องที่เหลือคือ negative ฟรี และ loss คือ softmax ของแต่ละแถว}}

**ตัวอย่าง: MNRL กับ batch ขนาด 3 ทีละขั้น (ตัวเลขสมมติ)** มี 3 คู่คำถามกับคำตอบ (q₁,p₁), (q₂,p₂), (q₃,p₃) ตารางความคล้าย sim(qᵢ, pⱼ) เป็นดังนี้ ช่องแนวทแยงคือคู่จริง

| | p₁ | p₂ | p₃ |
|---|---|---|---|
| q₁ | 0.9 | 0.2 | 0.1 |
| q₂ | 0.3 | 0.8 | 0.2 |
| q₃ | 0.1 | 0.4 | 0.7 |

ทำทีละแถว ใช้แถว q₁ และ τ = 1 เป็นตัวอย่าง

1. exp(0.9) = 2.4596, exp(0.2) = 1.2214, exp(0.1) = 1.1052 รวมกันได้ 4.7862
2. P(p₁ | q₁) = 2.4596 / 4.7862 = 0.5139
3. loss ของแถวนี้ = −log(0.5139) = 0.6657
4. ทำแบบเดียวกันกับแถว q₂ และ q₃

| τ | P ของคู่จริง (q₁, q₂, q₃) | loss ต่อแถว | loss เฉลี่ย |
|---|---|---|---|
| 1 | 0.5139, 0.4640, 0.4368 | 0.6657, 0.7679, 0.8284 | 0.7540 |
| 0.1 | 0.9988, 0.9909, 0.9503 | 0.0012, 0.0092, 0.0509 | 0.0205 |

- แต่ละ query มี negative 2 ตัว (N − 1 = 2) โดยไม่ต้องหามาเอง
- τ ต่ำ (0.1) ทำให้ softmax คม โมเดลมั่นใจกับคู่จริงมากขึ้น loss เลยต่ำลงมาก

**ตารางเทียบ loss (ต้องจำ)**

| Loss | รูปแบบข้อมูล | Negative | Margin | ใช้กับ |
|---|---|---|---|---|
| Softmax CE | (A,B,label) | โดยนัย | – | NLI |
| MSE | (A,B,score) | – | – | STS |
| Triplet | (a,p,n) | ระบุเอง | α | retrieval |
| Margin Ranking | (a,p,n) | ระบุเอง | α | retrieval |
| MNRL/InfoNCE | (q,p) | in-batch | τ | retrieval สมัยใหม่ |
| Cosine Similarity Loss | (A,B,y∈{−1,1}) | โดยนัย | – | คู่ similar/dissimilar |

**เลือก loss ตามข้อมูลที่มี:** มี label สามชั้น (NLI) ใช้ softmax cross-entropy, มีคะแนนต่อเนื่อง (STS) ใช้ MSE บน cosine, มีสามชุด (a, p, n) ใช้ triplet หรือ margin ranking, มีเฉพาะคู่ positive ใช้ MNRL ซึ่งสไลด์ 31 บอกว่านิยมที่สุดในปี 2026 เพราะรูปแบบข้อมูลง่ายสุด และสูตรสมัยใหม่ของสไลด์ 33 คือ AllNLI triplets + MNRL

## 7. SimCSE (Gao et al. 2021) (สไลด์ 24)

> **พูดง่าย ๆ:** ไม่มี label ก็ฝึกได้ โดยถามประโยคเดียวกันกับโมเดลสองรอบ แต่สุ่มปิดเซลล์สมองคนละชุด คำตอบสองรอบจะต่างกันนิดเดียว นำมาใช้เป็น "คู่เพื่อน" ได้ฟรี

**ศัพท์ก่อนอ่าน:**

- dropout (การสุ่มปิดบางส่วนของโมเดลตอนฝึก โมเดลต้องเปิดโหมดฝึกจึงจะทำงาน)
- augmentation (การสร้างตัวอย่างใหม่จากตัวอย่างเดิมโดยเปลี่ยนเล็กน้อย)
- representation collapse (เวกเตอร์ทุกตัวยุบกลายเป็นเกือบเหมือนกันหมด)
- eval mode (โหมดใช้งานของโมเดลที่ปิด dropout)
- unsupervised และ supervised (ไม่ใช้ label และใช้ label)

- **Unsupervised:** ส่งประโยคเดียวกันผ่าน BERT **สองรอบ** ด้วย dropout mask ต่างกัน ได้ positive pair ส่วนประโยคอื่นใน batch คือ negative ได้ ~76.3 บน STS **โดยไม่ใช้ label** ซึ่งสูงกว่า SBERT-base (74.89)
- **Supervised:** ใช้ NLI เดียวกัน โดย entailment = positive, contradiction = **hard negative** ได้ ~81.6
- ใช้ loss ตัวเดียวกับ MNRL เพียงเปลี่ยนวิธีสร้าง positive

**ทำไม dropout สร้าง positive pair ได้:** การส่งประโยคเดียวกันผ่านเครือข่ายสองรอบโดยเปิด dropout จะสุ่ม mask ต่างกันในแต่ละรอบ จึงได้เวกเตอร์ของประโยคเดิมที่ต่างกันเล็กน้อย ใช้เป็น "คู่ที่ความหมายเหมือนกัน" ได้โดยไม่ต้องมี label

**ตัวอย่าง: unsupervised SimCSE กับ batch 3 ประโยค (เป็นภาพประกอบ ไม่ใช่ตัวเลข)**

| ประโยค | รอบที่ 1 (dropout ชุด a) | รอบที่ 2 (dropout ชุด b) | positive ของรอบที่ 1 |
|---|---|---|---|
| X₁ | v₁ᵃ | v₁ᵇ | v₁ᵇ |
| X₂ | v₂ᵃ | v₂ᵇ | v₂ᵇ |
| X₃ | v₃ᵃ | v₃ᵇ | v₃ᵇ |

1. ประโยค X₁ ผ่านสองรอบ ได้เวกเตอร์ v₁ᵃ กับ v₁ᵇ ที่ต่างกันเล็กน้อย จึงเป็น positive
2. ประโยคอื่นใน batch คือ X₂ และ X₃ จึงเป็น negative ของ X₁ (ตามรูปแบบ MNRL ที่เป็น N − 1 = 2 ตัว)
3. ใช้ loss ตัวเดียวกับ MNRL ได้เลย เพียงเปลี่ยนวิธีสร้างคู่ positive

**ถ้าปิด dropout (โมเดลอยู่ใน eval mode) ทั้งสองรอบ:** สองเวกเตอร์เหมือนกันทุกประการ positive pair ไม่มี noise จึงแทบไม่ให้สัญญาณที่เป็นประโยชน์ (negative ใน batch ยังมีอยู่) เปเปอร์ SimCSE ระบุว่าการเอา dropout ออกทำให้เกิด representation collapse

**ตัวเลขเปรียบเทียบ (สไลด์ 24):** unsupervised 76.3, supervised 81.6, SBERT-base 74.89 คำนวณเองได้ว่า unsupervised สูงกว่า SBERT-base 1.41 จุด (76.3 − 74.89), supervised สูงกว่า 6.71 จุด (81.6 − 74.89) และ supervised สูงกว่า unsupervised 5.3 จุด (81.6 − 76.3) ซึ่งมาจาก entailment (positive) และ contradiction (hard negative) ของ NLI

**มุมมอง alignment/uniformity (ข้อความจากเปเปอร์ที่สไลด์ 24 แสดง):** unsupervised SimCSE ช่วยเรื่อง uniformity โดยไม่ทำให้ alignment เสียเพราะ noise จาก dropout ส่วนสัญญาณ NLI ช่วยเรื่อง alignment ของคู่ positive

**แยกกับ SBERT ให้ออก:** SBERT แบบ supervised ใช้ classification บน `[u; v; |u−v|]` ส่วน supervised SimCSE ใช้ contrastive loss (in-batch negative) กับ entailment และ contradiction

## 8. การเทรนสมัยใหม่และข้อมูล (สไลด์ 34-35)

> **พูดง่าย ๆ:** โมเดลสมัยใหม่เก่งเพราะอ่านคู่ (คำถาม, เอกสาร) จากเว็บนับร้อยล้านคู่ แล้วค่อยปรับละเอียดด้วยข้อมูลที่คนตรวจแล้ว เหมือนเรียนกว้างก่อนแล้วฝึกฝีมือกับครูเฉพาะทาง

**ศัพท์ก่อนอ่าน:**

- weakly-supervised (ใช้ label ที่ได้มาอัตโนมัติและไม่สะอาดเต็มที่ เช่น คู่ที่ขุดจากเว็บ)
- instruction tuning (ฝึกให้โมเดลทำตามคำสั่งนำหน้าข้อความ เช่น ระบุว่ากำลังค้นหาหรือจับคู่)
- gold, silver, weak (คุณภาพข้อมูล สูงสุดคือมนุษย์ทำป้ายเอง ต่ำสุดคือขุดจากเว็บ)
- CommonCrawl (คลังข้อมูลเว็บขนาดใหญ่ที่เปิดให้ดาวน์โหลด)

ไทม์ไลน์: 2019 SBERT (NLI+STS) → 2021 SimCSE → 2022 **E5** (weakly-supervised บนคู่ query-passage จาก CommonCrawl) → 2023 **BGE** (+ instruction tuning) → 2024-2026 instruction-based embeddings โมเดลสมัยใหม่เทรนบนคู่ (query, document) จากเว็บขนาดมหาศาล จึงชนะ SBERT ชัดเจน

| แหล่งข้อมูล | ขนาด | ชนิด |
|---|---|---|
| SNLI + MultiNLI (AllNLI) | ~1M คู่ | label entailment |
| STS Benchmark | ~8.5K คู่ | คะแนน 0-5 |
| MS MARCO | ~500K+ คู่ | query → passage |
| Quora Duplicate | ~400K คู่ | duplicate / ไม่ |
| Web-mined (E5, BGE) | 100M-1B+ | weak supervision |

ระดับคุณภาพ: Gold (human-annotated: NLI, STS) → Silver (curated: MS MARCO) → Weak (web-mined) สูตรสมัยใหม่: **pre-train ด้วย weak ขนาดใหญ่ แล้ว fine-tune ด้วย gold**

**ตัวอย่าง: ทีมมีข้อมูลแบบไหน ใช้อะไรได้ (ตัวเลขสมมติ)**

| สิ่งที่ทีมมี | เลือกใช้ | เหตุผลโดยสรุป |
|---|---|---|
| คู่ (คำถาม, ย่อหน้าที่ตอบ) 300 คู่ที่ทีมเขียนเอง | MNRL | ต้องการแค่คู่ positive (สไลด์ 30-31) |
| คู่ประโยคพร้อมคะแนนความคล้าย 0-5 | MSE บน cosine | คะแนนต่อเนื่อง (สไลด์ 23) |
| ไม่มีข้อมูลที่ติดป้ายเลย มีแต่ข้อความดิบ | SimCSE แบบ unsupervised หรือใช้โมเดลสำเร็จรูปที่ฝึกมาแล้ว | ไม่ต้องใช้ label (สไลด์ 24, 34) |

**รายละเอียดของไทม์ไลน์ (สไลด์ 34)**

- E5 ย่อมาจาก "Embeddings from bidirectional Encoder representations" เทรนแบบ weakly-supervised บนคู่ (query, passage) ที่ขุดจาก CommonCrawl
- BGE (BAAI) ใช้แนวทางคล้าย E5 บวก instruction tuning เช่นใส่คำนำ "Represent this sentence: ..." หน้าข้อความ
- ช่วง 2024-2026 เป็น instruction-based embeddings: โมเดลสร้างเวกเตอร์ต่างกันตามเจตนาของการเข้ารหัส
- ข้อสรุปของสไลด์: โมเดลสมัยใหม่ชนะ SBERT ชัดเจน เพราะเทรนบนคู่ (query, document) จากเว็บขนาดมหาศาล ไม่ใช่เพียง NLI และ STS

## 9. Vector Database และ ANN (สไลด์ 36, 39-40)

> **พูดง่าย ๆ:** Flat คือเดินหาหนังสือทีละเล่มทุกชั้น แม่นแต่ช้า HNSW คือมีทางด่วนพาไปใกล้ชั้นที่ต้องการก่อน IVF คือแบ่งห้องสมุดเป็นโซนแล้วค้นเฉพาะโซนที่ใกล้ PQ คือย่อรูปหนังสือให้เล็กลงจะได้ใส่ในตู้เล็ก ๆ ได้

**ศัพท์ก่อนอ่าน:**

- brute-force หรือ exact search (เทียบกับทุกเวกเตอร์ ได้คำตอบถูกแน่นอน)
- ANN (Approximate Nearest Neighbor ค้นเพื่อนบ้านใกล้สุดแบบประมาณ ยอมพลาดบ้าง)
- index (โครงสร้างข้อมูลที่ช่วยให้ค้นเร็ว)
- RAM (หน่วยความจำหลักของเครื่อง ถ้า index ใหญ่เกิน RAM จะรันไม่ได้)
- float32 (ตัวเลขทศนิยมที่ใช้ 4 ไบต์ต่อค่า)
- latency (เวลารอผลต่อหนึ่งคำค้น)
- Recall@k ในหัวข้อนี้ (สัดส่วนที่ ANN หาเจอเทียบกับ exact search)

- ขนาดหน่วยความจำของเวกเตอร์ = **n × d × 4 ไบต์** (float32 ใช้ 4 ไบต์ต่อค่า): 1M × 768 × 4 = 3,072,000,000 ไบต์ = 3.072 GB ซึ่งสไลด์ปัดเป็น ≈ 3 GB
- เวลา brute-force ต่อ query คือ O(n·d) หรือ n × d การดำเนินการ: สไลด์ 36 ระบุว่า 10M เอกสาร × 768 มิติ ใช้ราว 7.7 วินาทีที่ 1 GHz (นับเป็น 10⁹ การดำเนินการต่อวินาที: 10,000,000 × 768 / 10⁹ = 7.68 วินาที)
- **ANN** ยอมเสียความแม่นยำเล็กน้อยเพื่อความเร็วมาก (ราว 99% recall ได้เร็วขึ้น ~100 เท่า) อัลกอริทึม: FAISS (Facebook), HNSW, Annoy (Spotify), ScaNN (Google)
- กฎสำคัญ: **เทียบความเร็ว ANN โดยไม่รายงาน Recall@k ถือว่าไม่ถูกต้อง**
- ระบบ: Pinecone, Weaviate, Qdrant, Milvus, Chroma; ฝังในฐานข้อมูล: pgvector, SQLite-VSS; ไลบรารี: FAISS, ScaNN

| Index | วิธี | เวลาต่อ query (สไลด์ 39) | Recall | เหมาะกับ |
|---|---|---|---|---|
| Flat | brute-force แม่นยำ 100% | O(n·d) | 100% | corpus เล็ก (<100K) |
| IVF | แบ่งคลัสเตอร์ | ≈ O(√n·d) | ~95% | corpus ใหญ่ หน่วยความจำจำกัด |
| **HNSW** | กราฟหลายชั้น | ≈ O(log n·d) | ~99% | ระบบ production ส่วนใหญ่ |
| IVF+PQ | คลัสเตอร์ + บีบอัด | เร็วมาก RAM ต่ำ | ~90% | ระดับพันล้านเรคอร์ด |

- สไลด์เขียนเวลาของ IVF และ HNSW ด้วยเครื่องหมาย ≈ แปลว่าเป็นค่าประมาณตามสังเกต (empirical) บนข้อมูลที่ไม่ผิดปกติ ไม่ใช่การรับประกันทางทฤษฎี
- ความหมายของชื่อ (ความรู้ทั่วไป ไม่ใช่สไลด์): IVF คือการแบ่งเวกเตอร์เป็นคลัสเตอร์แล้วค้นเฉพาะคลัสเตอร์ที่ใกล้ query ส่วน PQ (product quantization) คือการบีบอัดเวกเตอร์ให้เล็กลง ซึ่งเป็นที่มาของ RAM ต่ำและ recall ต่ำสุดในตาราง
- ชื่อ Flat หมายถึงเก็บเวกเตอร์เต็ม ๆ ไม่บีบอัด ดังนั้น `IndexFlatIP` และ `IndexHNSWFlat` ใช้ RAM สำหรับเวกเตอร์เท่าสูตร n × d × 4 ไบต์ (เป็นความรู้ทั่วไปจากชื่อ index ในเดโม) การเปลี่ยนจาก IP เป็น L2 ไม่ลดหน่วยความจำ

เกณฑ์ปฏิบัติ: corpus <1M ใช้ HNSW; >1B ใช้ IVF+PQ

- สไลด์ 39 อธิบายว่า exact search การันตี top-k ถูกต้อง 100% แต่ไม่เหมาะเมื่อ n > 100K ส่วน ANN ใช้ index ตัดพื้นที่ค้นหาและได้ recall สูง (> 95%) ในเวลาที่โตแบบ sublinear เชิงสังเกต ส่วน FAISS (Facebook AI Similarity Search) รองรับ GPU และรองรับทุกชนิด index รวมถึงการประกอบกัน และสไลด์เรียกว่ามาตรฐานอุตสาหกรรม
- สไลด์ 40 บอกว่า HNSW เป็นค่าตั้งต้นของ Qdrant, Weaviate และ Pinecone เพราะ recall 99%+ (ชั้นบนเบาบางเป็นจุดเข้า ชั้นล่างสุดหนาแน่นมีข้อมูลทุกจุด)
- ลำดับความคิดของสไลด์ 36-40: ปัญหาคือหน่วยความจำและเวลา brute-force → ใช้ ANN ยอมเสีย recall เล็กน้อย → เลือก index ตามขนาด corpus และ RAM → **ต้องวัด Recall@k ทุกครั้ง** (สไลด์ 37)

**ตัวอย่าง: คำนวณหน่วยความจำและเวลาของคลังแนวทางการรักษา (ตัวเลขสมมติ)** สมมติมี 50 เอกสาร ตัดเป็น 40 chunk ต่อเอกสาร ใช้โมเดล 768 มิติ

1. จำนวน chunk = 50 × 40 = 2,000
2. หน่วยความจำ = 2,000 × 768 × 4 = 6,144,000 ไบต์ ≈ 6.144 MB เล็กมาก
3. brute-force ต่อ query ตามสูตรสไลด์ 36 = 2,000 × 768 = 1,536,000 การดำเนินการ = 0.001536 วินาที = 1.536 ms ที่ 1 GHz
4. สรุป: ระดับนี้ใช้ Flat ได้สบาย ไม่ต้องใช้ ANN

ถ้าขยายเป็นหนึ่งล้านชิ้น: 1,000,000 × 384 × 4 = 1.536 GB (โมเดล 384 มิติ) หรือ 1,000,000 × 768 × 4 = 3.072 GB (โมเดล 768 มิติ) ตอนนั้นการเลือก index และ RAM จึงเริ่มสำคัญ

**HNSW (Hierarchical Navigable Small World):** กราฟหลายชั้น ชั้นบนเบาบางไว้กระโดดไกล ชั้นล่างสุด (layer 0) หนาแน่นมีทุกจุด ค้นแบบหยาบไปละเอียด: เข้าชั้นบน → greedy walk หาเพื่อนบ้านใกล้สุด → ลงชั้นถัดไปทำซ้ำจนถึง layer 0 สไลด์ย้ำว่าความเร็ว sublinear เป็นแบบ empirical ขึ้นกับ efSearch การสร้างกราฟ และข้อมูล จึงต้องรายงาน Recall@k และ latency ที่วัดจริง

## 10. FAISS 5 ขั้นตอน (สไลด์ 38, 41-43)

> **พูดง่าย ๆ:** FAISS คือตู้เก็บเวกเตอร์ที่ค้นเร็ว ขั้นตอนคือเตรียมเวกเตอร์ ปรับความยาวให้เท่ากัน ใส่เข้าตู้ แล้วถามด้วยเวกเตอร์ของคำค้นที่ปรับความยาวแบบเดียวกัน

**ศัพท์ก่อนอ่าน:**

- FAISS (ไลบรารีค้นเวกเตอร์ของ Facebook)
- inner product หรือ IP (ผลคูณจุด ถ้าเวกเตอร์ยาว 1 จะเท่ากับ cosine)
- `D` และ `I` (ผลที่ `search` ส่งกลับ D คือคะแนน I คือลำดับที่ของเอกสาร)
- offline และ online (ทำล่วงหน้าครั้งเดียว และทำทุกครั้งที่มีคำค้น)

1. เตรียมเวกเตอร์ `[n, d]` ชนิด **float32**
2. `faiss.normalize_L2(vectors)` ขั้นวิกฤต: ไม่ทำแล้วผลถูกครอบงำด้วยขนาด
3. `faiss.IndexFlatIP(d)` (inner product)
4. `index.add(vectors)`
5. normalize query แบบเดียวกัน แล้ว `D, I = index.search(q, k)` ได้ D = คะแนน, I = ดัชนีเอกสาร (ทั้งคู่ `[1, k]`)

**ตัวอย่าง: 5 ขั้นกับเอกสาร 3 ชิ้น (ตัวเลขสมมติ 2 มิติ)** เอกสาร d1 = [3, 4], d2 = [0, 5], d3 = [10, 0] และ query q = [6, 8]

1. เตรียมเวกเตอร์ชนิด float32
2. normalize เอกสาร: d1 → [0.6, 0.8], d2 → [0, 1], d3 → [1, 0]
3. สร้าง `IndexFlatIP(2)` แล้ว `add` ทั้งสามชิ้น
4. normalize query: [6, 8] → [0.6, 0.8]
5. `search` ด้วย k = 2 ได้คะแนน inner product ของแต่ละชิ้น: d1 = 0.6×0.6 + 0.8×0.8 = 1.0, d2 = 0.8, d3 = 0.6 ได้ `D = [[1.0, 0.8]]` และ `I = [[0, 1]]` (ค่าจริงในเครื่องอาจคลาดเคลื่อนทศนิยมเล็กน้อย)

ถ้าข้ามการ normalize และใช้ dot product ตรง ๆ: d1 = 50, d2 = 40, d3 = 60 อันดับ 1 จะกลายเป็น d3 ซึ่งผิด เพราะ d3 แค่ยาวกว่า ไม่ได้ชี้ทิศใกล้ query ที่สุด

**ทำไมใช้ `IndexFlatIP` ไม่ใช่ `IndexFlatL2`:** หลัง normalize แล้ว IP = cosine อ่านง่าย (ยิ่งสูงยิ่งดี ช่วง [−1,1]) ส่วน L2 คืนระยะทางกำลังสอง (ยิ่งต่ำยิ่งดี) อ่านและตั้ง threshold ยากกว่า

**เลือก metric ตามงาน (สไลด์ 42)**

| งาน | metric | เหตุผล |
|---|---|---|
| Semantic search | Cosine | ทิศทางสำคัญ ขนาดไม่สำคัญ |
| Document retrieval | Dot product (หลัง normalize) | เท่า cosine และเร็วที่สุด |
| Image similarity | Cosine | CLIP embedding มีทิศทาง |
| Anomaly detection | L2 | ระยะห่างสัมบูรณ์สำคัญ |
| RAG retrieval | Cosine | มาตรฐานของ SBERT/E5/BGE |

ความผิดพลาดที่พบบ่อยคือใช้ L2 กับเวกเตอร์ที่ไม่ได้ normalize

เหตุผลคือเวกเตอร์ที่ยาวต่างกันจะดูไม่คล้ายกันใน L2 แม้ชี้ทิศเดียวกัน และ dot product จะให้คะแนนสูงกับเวกเตอร์ที่ยาว ผลคือ `IndexFlatIP` จัดอันดับตาม **ความยาวของเวกเตอร์ ไม่ใช่ความหมาย** ทางแก้คือ normalize เองเสมอทั้งเวกเตอร์เอกสารและ query ด้วยวิธีเดียวกัน แม้ `.encode()` ของบางโมเดลจะ normalize ให้อยู่แล้ว (ดูหัวข้อเดโม)

**Pipeline ครบวงจร (สไลด์ 43)**

- ออฟไลน์ (ทำครั้งเดียว): โหลดเอกสาร → `model.encode(documents)` → normalize → `index.add` → บันทึก index
- ออนไลน์ (ทุก query): encode query → normalize → `index.search(q, k=10)` → คืนเอกสารตามคะแนน
- latency: encode ~5-10ms (GPU) / ~50ms (CPU), search <1ms (exact 100K) / <5ms (ANN 10M), รวม <20ms บน GPU

{{fig:week09-search-pipeline | pipeline ค้นหาเชิงความหมายสองช่วง: ช่วงออฟไลน์สร้างและบันทึก FAISS index ครั้งเดียว ช่วงออนไลน์ encode และ normalize query แบบเดียวกันก่อนค้น}}

**กิจกรรมสไลด์ 44:** 5 ล้านบทคัดย่อ, โมเดล all-mpnet-base-v2 (768 มิติ), RAM 32 GB, A100 หนึ่งใบ, ต้องตอบภายใน 50 ms

1. หน่วยความจำ: 5,000,000 × 768 × 4 = 15,360,000,000 ไบต์ = 15.36 GB (= 14.31 GiB) น้อยกว่า 32 GB แต่เหลือที่ให้ระบบและ overhead ของ index ไม่มาก
2. metric: cosine ผ่านการ L2-normalize แล้วใช้ inner product (สไลด์ 42 ระบุว่า document retrieval ใช้ dot product หลัง normalize)
3. index: brute-force ต้องทำ n × d = 5,000,000 × 768 = 3.84 × 10⁹ การดำเนินการต่อ query หรือ 3.84 วินาทีที่ 1 GHz ตามสูตรของสไลด์ 36 เกินเพดาน 50 ms มาก และสไลด์ 39 บอกว่า Flat ไม่เหมาะเมื่อ n > 100K จึงควรใช้ ANN โดย HNSW เป็นตัวเลือกที่สไลด์ให้สำหรับ corpus ที่ไม่ถึงระดับพันล้าน เกณฑ์ของสไลด์ (< 1M → HNSW, > 1B → IVF+PQ) ไม่ได้ครอบคลุม 5M โดยตรง จึงเป็นการตัดสินใจเชิงวิศวกรรมที่ต้องวัด Recall@k คู่กับ latency (สไลด์ไม่ได้ให้ตัวเลขของการค้นแบบ exact บน GPU)
4. normalize: ทำตอน offline กับเวกเตอร์เอกสารก่อน `add` และทำกับ query ทุกครั้งก่อน `search` ด้วยวิธีเดียวกัน (สไลด์ 41 และ 43)

**กิจกรรมสไลด์ 25 (ออกแบบ pipeline ด้วย bi-encoder):** ตั๋วร้องเรียนภาษาไทย 100,000 ใบ มีตั๋วใหม่เข้ามา ต้องหา 5 ใบที่คล้ายที่สุด สไลด์ให้ตอบสี่ช่วง (เฉลยด้านล่างเป็นแนวตอบจากเนื้อหาสัปดาห์นี้ สไลด์ไม่ได้เฉลย)

1. Encoding: ใช้ bi-encoder แบบ SBERT/sentence-transformers (โมเดลที่ fine-tune ด้วย contrastive loss) pooling แบบ masked mean ซึ่งเป็นค่าเริ่มต้นและชนะ CLS มิติเอาต์พุตเท่ากับ d ของโมเดล (384, 768 หรือ 1024) ข้อควรระวังที่เป็นความรู้ทั่วไป ไม่ใช่สไลด์: งานเป็นภาษาไทย ต้องเลือกโมเดลที่ฝึกกับข้อความไทยหรือหลายภาษา เพราะ all-MiniLM-L6-v2 ในตารางสไลด์ 20 ฝึกกับข้อความอังกฤษเป็นหลัก
2. Indexing: encode ตั๋วทั้งหมดครั้งเดียวแบบออฟไลน์ → L2-normalize → `IndexFlatIP(d)` → `index.add` → บันทึก index หน่วยความจำ (d = 768) = 100,000 × 768 × 4 = 307,200,000 ไบต์ = 0.3072 GB (307.2 MB) เล็กมาก จำนวน 100,000 อยู่ที่ขอบของเกณฑ์ "Flat เหมาะกับ corpus < 100K" (สไลด์ 39) จึงเลือก Flat (exact) ได้ หรือเปลี่ยนเป็น HNSW ถ้าค่า latency ไม่พอ
3. Query: encode ตั๋วใหม่ด้วยโมเดลและ pooling เดียวกัน → normalize ด้วยวิธีเดียวกัน → inner product กับเวกเตอร์ทั้งหมด (= cosine เพราะ normalize แล้ว) ต้นทุน brute-force ตามสูตรสไลด์ 36 = 100,000 × 768 = 7.68 × 10⁷ การดำเนินการ = 0.0768 วินาทีที่ 1 GHz ส่วนสไลด์ 43 ระบุว่าการค้นแบบ exact บน 100K เวกเตอร์ใช้ < 1 ms สองตัวเลขนี้ไม่เท่ากัน สไลด์ 36 เป็นสูตรประมาณ (1 การดำเนินการต่อรอบสัญญาณนาฬิกา) สไลด์ 43 เป็นค่าทั่วไป ถ้าโจทย์ให้สูตรให้คำนวณตามสูตรที่โจทย์ให้
4. Ranking: `D, I = index.search(q, k=5)` ได้คะแนน cosine และดัชนีของ 5 ใบอันดับสูงสุด (เรียงจากมากไปน้อย) แล้วใช้ `I` ไปค้นข้อความต้นฉบับ
5. คำถามอภิปราย "cross-encoder อยู่ตรงไหน": ใส่เป็นขั้นที่สอง re-rank ผู้สมัครที่ bi-encoder ดึงมา (เช่น top-20 หรือ top-100) เพื่อเพิ่ม precision ตามสไลด์ 18

**สไลด์ 45 (แผนภาพสถาปัตยกรรมสัปดาห์ 9):** สไลด์เป็นรูป สายหลักคือ BERT Encoder (shared) → Mean Pooling Layer → L2 Normalize → Vector Index (FAISS/HNSW) → Similarity Search → Top-k Results ส่วน query (ข้อความ) วิ่งผ่าน **pipeline เข้ารหัสเดียวกัน** แล้วเข้าสู่ similarity search ด้านล่างของ BERT Encoder มีกล่อง "NLI / STS / MS MARCO Training Data" เชื่อมด้วยลูกศร "Contrastive Training (SBERT)" ที่ปรับน้ำหนักของ encoder ข้อความบนสไลด์สรุปเรื่องราวไว้สามบรรทัด: ปัญหา = objective MLM ไม่ปรับ geometry ของประโยค จึงเกิด anisotropy และ embedding เสียหาย, วิธีแก้ = Siamese fine-tuning ด้วย contrastive loss ได้ SBERT, การใช้งาน = Encode → Index → Search → Retrieve ประเด็นที่ออกข้อสอบได้คือ **ลำดับของขั้นตอน** (normalize มาหลัง pooling และก่อน index) และการที่ query ต้องใช้ encoder ตัวเดียวกับเอกสาร

## 11. วัดคุณภาพการค้นหา (สไลด์ 37)

> **พูดง่าย ๆ:** Recall@k ถามว่า "คำตอบที่ถูกอยู่ใน k อันดับแรกครบแค่ไหน" MRR ถามว่า "คำตอบถูกตัวแรกโผล่ขึ้นมาเร็วแค่ไหน" ระบบที่เจอคำตอบแต่ฝังอยู่ท้ายรายการ จะ Recall ดีแต่ MRR ต่ำ

**ศัพท์ก่อนอ่าน:**

- relevant (เอกสารที่ตอบคำถามนั้นได้จริงตามเฉลย)
- rank (อันดับที่เอกสารปรากฏในผลลัพธ์ อันดับ 1 คือบนสุด)
- reciprocal rank (หนึ่งส่วนอันดับ เช่น อันดับ 3 ได้ 1/3)
- precision@k (สัดส่วนของ k อันดับแรกที่ถูกต้อง)
- query (คำค้นหรือคำถามที่ป้อนเข้าระบบ)

- **Recall@k** = `|Retrieved_k ∩ Relevant| / |Relevant|` (ครอบคลุมแค่ไหน)
- **MRR** = `(1/|Q|) Σ 1/rankᵢ` (เอกสารถูกต้องตัวแรกอยู่อันดับเท่าไร อันดับ 1 → 1.0, อันดับ 2 → 0.5)
- ใช้ตรวจว่า ANN ที่เร็วขึ้นไม่ทำให้คุณภาพตก
- Recall@k หารด้วย **จำนวนเอกสารที่เกี่ยวข้องทั้งหมด** (|Relevant|) ส่วน precision@k หารด้วย k (จำนวนที่ดึงมา) เช่น มี relevant 4 ฉบับ พบใน top-10 จำนวน 3 ฉบับ: Recall@10 = 3/4 = 0.75 ส่วน precision@10 = 3/10 = 0.30 (precision ไม่อยู่ในสไลด์ แต่ใช้เป็นตัวหลอกในชุดฝึกซ้อม)
- MRR ใช้เฉพาะ **เอกสารที่ถูกต้องอันแรก** ของแต่ละ query แล้วเฉลี่ย 1/rank ข้าม query: ถ้าอันดับแรกของสาม query คือ 1, 2, 4 ได้ (1 + 0.5 + 0.25)/3 = 0.5833
- อันดับ 4 ให้ reciprocal rank = 1/4 = 0.25 (ไม่ใช่ 4 และไม่ใช่ 0.75)
- ถ้า query ไหนหาเอกสารถูกต้องไม่เจอเลย reciprocal rank นับเป็น 0 (ความรู้ทั่วไป ไม่ได้อยู่ในสไลด์)
- Recall@k บอกว่าเจอครบแค่ไหน ส่วน MRR บอกว่าเจอเร็วแค่ไหน ระบบที่ Recall@5 สูงแต่ MRR ต่ำ คือเจอแต่เอกสารไปอยู่ท้ายรายการ ซึ่งเป็นเหตุผลที่ต้องมี cross-encoder จัดอันดับใหม่

**ตัวอย่าง: 3 query ใช้ top-5 (ตัวเลขสมมติ)**

| query | เอกสารที่เกี่ยวข้องทั้งหมด | ที่พบใน top-5 | Recall@5 | reciprocal rank |
|---|---|---|---|---|
| Q1 | 2 (A, B) | A อันดับ 1 ส่วน B ไม่อยู่ใน top-5 | 1/2 = 0.5 | 1/1 = 1 |
| Q2 | 1 (C) | C อันดับ 3 | 1/1 = 1 | 1/3 = 0.3333 |
| Q3 | 1 (D) | ไม่พบ | 0/1 = 0 | 0 |

1. Recall@5 เฉลี่ย = (0.5 + 1 + 0) / 3 = 0.5
2. MRR = (1 + 0.3333 + 0) / 3 = 0.4444
3. อ่านผล: ระบบเจอคำตอบครึ่งหนึ่ง และคำตอบแรกที่ถูกโผล่เฉลี่ยค่อนข้างท้าย ๆ

**เชื่อมกับโปรเจกต์:** คอร์สกำหนดอย่างน้อย 2 เมตริก Recall@k และ MRR ตรงกับเนื้อหานี้พอดี

## 12. แล็บของสัปดาห์ (สไลด์ 46) (ไม่ออกสอบ ตามที่อาจารย์บอก)

> **พูดง่าย ๆ:** แล็บคือการลองสร้างระบบค้นหาเชิงความหมายด้วยมือตั้งแต่ต้นจนจบ ไม่ออกสอบ แต่ช่วยให้เข้าใจขั้นตอนในหัวข้อก่อนหน้า

1. Manual SBERT inference: tokenize → forward → mean pooling → L2 normalize ด้วยมือ
2. พิสูจน์ anisotropy: เทียบ cosine ของ BERT ดิบกับ SBERT
3. สร้าง FAISS Inner Product index
4. เขียนลูปค้นหา แสดง top 2 และบันทึก index ไว้ใช้ในแล็บสัปดาห์ 12

ผลงานส่งมอบของแล็บคือระบบ semantic search ครบวงจรด้วย FAISS ที่พร้อมต่อกับสัปดาห์ 12 (สไลด์ 46) สไลด์ 46 ใช้สรุปเนื้อหาเท่านั้น ไม่ออกสอบเป็นข้อแล็บ

**สไลด์ 47-49 (สรุปปิดท้าย)**

- สไลด์ 47 ห้าข้อที่ต้องจำ: (1) anisotropy คืออาการ สาเหตุคือ objective MLM (2) Siamese/bi-encoder คือวิธีแก้ แชร์น้ำหนักและใช้ contrastive loss (3) mean pooling (ใช้ attention mask) ชนะ CLS (4) contrastive loss (triplet, MNRL ฯลฯ) ขับ geometry "คล้ายใกล้ ต่างไกล" (5) vector indexing (FAISS, ANN) ทำให้ค้นหาหลายล้านเอกสารได้จริง เป็นรากฐานของ RAG
- สไลด์ 48 สะพานไปสัปดาห์ 12: bi-encoder + FAISS index ของสัปดาห์นี้คือขั้น dense retrieval ของ RAG ลำดับเต็มคือ (1) dense retrieval (2) sparse retrieval ด้วย BM25 แล้วรวมด้วย Reciprocal Rank Fusion (RRF) (3) cross-encoder re-ranking (4) LLM generation ด้วย context ที่ดึงมา ภาพรวมของสไลด์: Retrieval (สัปดาห์ 9) + Efficiency (สัปดาห์ 10) + Alignment (สัปดาห์ 11) + Generation (สัปดาห์ 12) = ผู้ช่วย AI สมัยใหม่
- สไลด์ 49 อ่านเพิ่ม: Reimers & Gurevych (2019) หัวข้อ 1-4 (สถาปัตยกรรมและการทดลอง), Gao et al. (2021) SimCSE หัวข้อ 1-3 (ไม่บังคับ) และเก็บ FAISS index จากแล็บไว้ใช้ในสัปดาห์ 12

อาจารย์บอกว่าสิ่งที่แสดงเฉพาะในเดโม (ไม่อยู่ในสไลด์) อาจออกได้ราว 1-2 ข้อ รายการนี้มาจาก notebook ของสัปดาห์ 9 และตัวเลขเป็นผลที่รันได้จริงในไฟล์ (ไม่ใช่ค่าที่ผมคำนวณใหม่ ยกเว้นที่ระบุ)

**เดโมหัวข้อ 2: `[CLS]` ของ raw BERT กลับอันดับ** (`bert-base-uncased`)

- ประโยค A = "The cat sat on the mat." B = "I love training deep neural networks." (ไม่เกี่ยวกับ A) C = "Dogs are chasing cats in the park." (เกี่ยวกับ A)
- รูปร่าง `[CLS]` embeddings คือ `[3, 768]`
- cos(A, B) = 0.8610 สูงกว่า cos(A, C) = 0.7942 จึง **อันดับกลับด้าน** (ตัวเลขชุดนี้ตรงกับสไลด์ 12 ที่ปัดเป็น 0.86 และ 0.79)
- บทเรียนของเดโม: ดู **ลำดับ** และ **ค่าต่ำสุด (floor)** ไม่ใช่แค่ขนาดตัวเลข และสองคู่ไม่พอ ต้องวัดทั้งการกระจาย

**เดโมหัวข้อ 2b: วัด cone บน 12 ประโยค = 66 คู่ (12 × 11 / 2)**

| encoder | mean | min | max | range |
|---|---|---|---|---|
| raw BERT `[CLS]` | +0.768 | +0.561 | +0.942 | 0.380 |
| raw BERT mean-pooled | +0.580 | +0.457 | +0.848 | 0.391 |
| SBERT (all-MiniLM-L6-v2) | +0.057 | −0.156 | +0.556 | 0.712 |

- ดูคอลัมน์ **min**: raw BERT ไม่เคยต่ำกว่าประมาณ 0.457 ส่วน SBERT ลงถึง −0.156 (cosine ติดลบได้)
- raw BERT บีบ 66 คู่ไว้ในแถบกว้างประมาณ 0.39 ส่วน SBERT กระจาย 0.71
- ค่าเฉลี่ย 0.580 ของ mean-pooled ตรงกับ "เฉลี่ย 0.58" ของสไลด์ 19 ส่วน `[CLS]` มีค่าเฉลี่ย 0.768 สูงกว่า อย่าสับสนสองค่า
- ถ้อยคำของเดโม: cone ไม่ใช่ "ทุกคะแนน 0.99" แต่คือ "ไม่มีคะแนนไหนต่ำ จึงไม่มีที่ว่างให้แยกอะไรออกจากกัน"

**เดโมหัวข้อ 3: manual mean pooling**

- โค้ดทำ 5 ขั้น: ขยาย mask ด้วย `attention_mask.unsqueeze(-1).expand(token_embeddings.size()).float()`, คูณกับ embedding, รวมตามมิติความยาว (`sum(dim=1)`), รวม mask เพื่อนับ token จริง, แล้วหาร โดยใช้ `clamp(min=1e-9)` กันหารด้วยศูนย์
- ตัวอย่างโทเค็น `['[CLS]', 'the', 'cat', 'sat', 'on', 'the', 'mat', '.', '[SEP]', '[PAD]']` และ mask `[1, 1, 1, 1, 1, 1, 1, 1, 1, 0]` ผลลัพธ์รูปร่าง `[3, 768]`
- **`[PAD]` ไม่ใช่เวกเตอร์ใกล้ศูนย์:** ค่า L2 norm เฉลี่ยของ token จริง = 14.90 ส่วนของ `[PAD]` = 9.67 เพราะ `[PAD]` ถูก mask เฉพาะในฐานะ key แต่ยังมี position embedding ยังผ่าน feed-forward และ residual และยัง attend ไปหา token จริง การเฉลี่ยรวมจึงทำให้เวกเตอร์ประโยค **ถูกบิดเบือน** ไม่ใช่แค่เล็กลง
- verification: `SentenceTransformer('bert-base-uncased')` (ไม่มี pooling module ไลบรารีสร้าง mean pooling ให้อัตโนมัติ) ให้ผลตรงกับ manual ด้วย `torch.allclose(..., atol=1e-4)` ค่าต่างกันประมาณ 1e-7 ไม่ตรงทุกบิตเพราะลำดับการคำนวณต่างกัน
- แม้ mean pooling ถูกต้อง ถ้าโมเดลไม่ได้ fine-tune ด้วย contrastive loss เวกเตอร์ก็ยัง anisotropic

**เดโมหัวข้อ 4: all-MiniLM-L6-v2 (dim 384)**

- "A man is eating food." เทียบ "A man is eating pasta." ได้ 0.7035 (สูง)
- "A man is eating food." เทียบ "The girl is carrying a baby." ได้ −0.1050 (ต่ำ และติดลบได้)
- รูปร่างผลลัพธ์ `(3, 384)` และต้องสั่ง `encode(..., normalize_embeddings=True)` เองเมื่อต้องการเวกเตอร์ unit

**เดโมหัวข้อ 5: pipeline 5 ขั้นไม่ใช่ตัว SBERT**

- เดโมเตือนว่า 5 ขั้นเป็นแค่ "สถาปัตยกรรม" ตอน inference ถ้าทำ pooling และ normalize กับ raw BERT จะ **ไม่แก้ anisotropy** สิ่งที่แก้คือ contrastive fine-tuning
- norm ก่อน normalize ของเวกเตอร์ตัวอย่างสามตัว = 10.21, 8.63, 10.50 และหลัง normalize ≈ 1.0 ทั้งหมด

**เดโมหัวข้อ 6: Triplet และ Margin Ranking**

- `nn.MarginRankingLoss(margin)` เรียกเป็น `loss_fn(sim_pos, sim_neg, target)` โดย `target = +1` แปลว่า x₁ ควรสูงกว่า x₂ สูตรภายในคือ `max(0, −y·(x₁ − x₂) + margin)` = `max(0, sim_neg − sim_pos + margin)`
- `nn.TripletMarginLoss(margin=1.0, p=2)` คือ triplet แบบ Euclidean
- ตัวอย่าง anchor = [1, 1], positive = [1.2, 0.9], negative = [3, −1], margin = 0.5: sim(a,p) = 0.9899, sim(a,n) = 0.4472, margin ranking = 0 และ triplet แบบ cosine distance ก็ได้ 0 เท่ากัน (slack ก่อน clamp = −0.0427)
- แบบ Euclidean (margin = 1): d(a,p) = 0.2236, d(a,n) = 2.8284 ได้ loss 0 เช่นกัน แต่ slack = −1.6048 ต่างจาก cosine มาก สรุปว่า **metric เป็นส่วนหนึ่งของ loss** เพราะเป็นตัวกำหนดว่า triplet ไหนถือว่า "แก้เสร็จแล้ว"
- hard negative [1.05, 0.95]: sim(a, hard) = 0.9988 และ margin ranking loss = 0.5088 (มากกว่า 0 จึงเกิด gradient) เทียบกับ easy negative ที่ loss = 0 ซึ่งโมเดลไม่ได้เรียนรู้อะไร นี่คือเหตุผลของ hard/semi-hard mining

**เดโมหัวข้อ 7: FAISS**

- corpus 8 ประโยค query "What is a fast library for vector similarity search?" ค้นด้วย k = 3 ได้อันดับ 1 = ประโยคเรื่อง FAISS (0.5753), อันดับ 2 = ประโยคเรื่อง cosine similarity (0.5050), อันดับ 3 = ประโยคเรื่อง BERT (0.2321)
- **all-MiniLM-L6-v2 ส่งเวกเตอร์ unit มาให้อยู่แล้ว** (มีโมดูล Normalize ในโมเดล) norm ก่อนและหลัง normalize = 1.0 แต่เป็นสมบัติของ checkpoint นี้ ไม่ใช่ของ `.encode()` ทั่วไป ค่าเริ่มต้น `normalize_embeddings` เป็น False และโมเดลอย่าง BGE หรือ E5 ที่โหลดผ่าน transformers ดิบ ๆ จะไม่ normalize ให้
- เวกเตอร์ raw BERT mean-pooled มี norm ประมาณ 10.12, 9.97, 9.84, 8.94 (ยาวต่างกัน) หลัง `faiss.normalize_L2` ได้ 1.0 ทั้งหมด ถ้าข้ามขั้นนี้ `IndexFlatIP` จะจัดอันดับตามความยาว ไม่ใช่ความหมาย
- **`IndexHNSWFlat` ไม่ใช่ drop-in ของ `IndexFlatIP`:** ต้องระบุ M (ความเชื่อมต่อของกราฟ) เช่น `faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT)` และค่าเริ่มต้นเป็น **L2** ทำให้ D เป็นระยะทางกำลังสอง (ยิ่งต่ำยิ่งดี) กลับกับคะแนน cosine (ยิ่งสูงยิ่งดี) ความเร็ว sublinear เป็นแบบ empirical ขึ้นกับ M, efSearch และข้อมูล จึงต้องวัด Recall@k และ latency
- ข้อความเตือน "UNEXPECTED" ตอนโหลด `AutoModel` (เช่น `cls.predictions...`, `cls.seq_relationship...`) คือ head ของ MLM/NSP ที่ไม่ได้ใช้ถูกทิ้ง ซึ่งเป็นเรื่องปกติ ไม่ใช่ error (ข้อนี้เป็นความรู้ทั่วไป)

2. **ช่วง cosine ของ SBERT:** สไลด์ 19 ระบุ [0.1, 0.99] แต่เดโม 2b วัด all-MiniLM-L6-v2 ได้ [−0.156, +0.556] (ใช้ประโยคชุดอื่นและโมเดลอื่น) ใช้เลขสไลด์เมื่อโจทย์อ้างสไลด์ ใช้ข้อสรุปของเดโมที่ว่า SBERT ลดต่ำกว่า 0 ได้
3. **คะแนน SBERT-base:** 77.03 (สไลด์ 4, 19) เทียบ 74.89 (สไลด์ 24 ในบริบทเทียบ SimCSE) ผมไม่ได้ตรวจว่าวัดแบบเดียวกันหรือไม่
4. **เลขที่ปัด:** 58.02 / 46.35 (สไลด์ 4) เทียบ 58.2 / 46.4 (สไลด์ 19) เป็นค่าเดียวกัน
5. **มาตราคะแนน STS-B:** สไลด์ 23 ระบุ 0-5 แต่หน้าเปเปอร์ BERT ที่สไลด์ 18 แสดงเขียนว่า 1 ถึง 5 ให้ยึดสไลด์ 23 (0-5)
6. **ข้อกำหนดเลือก index:** เกณฑ์ของสไลด์คือ < 1M → HNSW และ > 1B → IVF+PQ ไม่ได้บอกกรณีกลาง (เช่น 5M หรือ 20M) โจทย์ที่ให้ข้อจำกัด RAM ต้องใช้เหตุผลจากขนาดหน่วยความจำ (n × d × 4) ประกอบ
7. **เวลาค้นแบบ exact บน 100K เวกเตอร์:** สูตรสไลด์ 36 (n × d / 10⁹ วินาทีที่ 1 GHz) ให้ 100,000 × 768 / 10⁹ = 0.0768 s แต่สไลด์ 43 ระบุ search < 1 ms (exact, 100K เวกเตอร์) ถ้าโจทย์ให้สูตรหรือให้ความเร็วเครื่องมา คำนวณตามนั้น ถ้าถามค่าทั่วไปของ pipeline ใช้ตัวเลขสไลด์ 43
8. **สะกดประโยคในสไลด์ 17:** สไลด์ 17 เขียน B = "A man is eating passta" ส่วนสไลด์ 22 เขียน pasta ให้ยึด shape [1,7] และ [1,8] ตามสไลด์

**คู่มือตัดสินใจแบบ if-then**

1. ถ้าต้องเทียบกับเอกสารหลายพันชิ้นขึ้นไปทุก query ให้ใช้ bi-encoder ถ้ามีเฉพาะผู้สมัครไม่กี่สิบชิ้นและต้องการความแม่นสูง ให้เพิ่ม cross-encoder จัดอันดับใหม่
2. ถ้าต้องสร้างเวกเตอร์จาก BERT ให้ใช้ masked mean pooling และอย่าใช้ BERT ดิบโดยไม่ fine-tune
3. ถ้ามีป้าย NLI ใช้ softmax; ถ้ามีคะแนน STS ใช้ MSE บน cosine; ถ้ามีเฉพาะคู่ positive ใช้ MNRL; ถ้ามี triplet ใช้ triplet loss
4. ถ้าไม่มี label เลย ให้ใช้ SimCSE หรือโมเดลสำเร็จรูป แล้ววัดผลกับชุดทดสอบของทีมเสมอ (ต่อยอดจากสไลด์)
5. ก่อนเข้า FAISS ให้ normalize เสมอ แล้วใช้ `IndexFlatIP`
6. ถ้า corpus ไม่ถึง 100K ใช้ Flat; ถ้า RAM พอและต้องเร็ว ใช้ HNSW; ถ้าถึงระดับพันล้านและ RAM จำกัด ใช้ IVF+PQ
7. วัดด้วย Recall@k และ MRR ทุกครั้งที่เปลี่ยนโมเดลหรือ index

**ห้าทางเลือกที่ผิดบ่อย และทำไมถึงพัง**

1. **ใช้ cross-encoder ค้นทั้งคลัง:** ต้องรันเป็นจำนวนคู่ n(n−1)/2 หรือ 1 ต่อ chunk ต่อ query จึงช้าจนใช้ไม่ได้ ควรใช้เฉพาะรอบจัดอันดับใหม่
2. **ใช้ `[CLS]` ของ BERT ดิบเป็นเวกเตอร์ประโยค:** `[CLS]` เทรนมาจาก NSP และ anisotropy ทำให้คู่ที่ไม่เกี่ยวข้องได้ cosine สูงกว่าคู่ที่เกี่ยวข้อง (0.86 เทียบ 0.79 ในสไลด์ 12)
3. **ใช้ `IndexFlatIP` โดยไม่ normalize:** อันดับถูกขนาดเวกเตอร์ครอบงำแทนที่จะเป็นความหมาย (สไลด์ 42)
4. **ใช้ label STS 0-5 ตรง ๆ กับ MSE บน cosine:** cosine ไม่เกิน 1 จึงไปไม่ถึง label ที่มากกว่า 1 โมเดลถูกดันให้ cos = 1 กับทุกคู่ที่ label ≥ 1 ต้องหารด้วย 5 ก่อน
5. **เปรียบเทียบความเร็ว ANN โดยไม่รายงาน Recall@k:** ANN เร็วเพราะยอมพลาด ถ้าไม่วัด Recall@k จะไม่รู้ว่าเร็วขึ้นแต่คำตอบหายไปมากแค่ไหน (สไลด์ 37)

### ประเภท 1: Cosine similarity และ dot product

สูตร: `cos(u,v) = u·v / (‖u‖‖v‖)`, `u·v = ‖u‖‖v‖cos(u,v)`

**1.1 สองมิติ** u = [3, 4], v = [4, 3]

1. u·v = 3×4 + 4×3 = 12 + 12 = 24
2. ‖u‖ = √(9+16) = 5, ‖v‖ = √(16+9) = 5
3. cos = 24 / (5×5) = 24/25 = 0.96
- ตอบ **0.96** กับดัก: ตอบ 24 (ลืมหารด้วยขนาด) ตรวจ: cos ต้องไม่เกิน 1

**1.2 สามมิติ** u = [1, 2, 2], v = [2, 1, 2]

1. u·v = 2 + 2 + 4 = 8
2. ‖u‖ = √(1+4+4) = 3, ‖v‖ = √(4+1+4) = 3
3. cos = 8/9 = 0.8889
- ตอบ **0.8889** (ปัดเป็น 0.889)

**1.3 เปลี่ยนสเกลของเวกเตอร์** u = [2, 1, 2], w = [6, 3, 6] (w = 3u)

1. u·w = 12 + 3 + 12 = 27, ‖u‖ = 3, ‖w‖ = √(36+9+36) = 9
2. cos = 27/(3×9) = 1.0
3. แต่ L2 distance = ‖u−w‖ = ‖[−4, −2, −4]‖ = √(16+4+16) = 6 ไม่ใช่ 0
- ตอบ cos = **1.0**, L2 = **6** บทเรียน: cosine ไม่สนขนาด ส่วน L2 สนขนาด (จึงต้อง normalize ก่อนใช้ L2) ตัวอย่างตรงข้าม: [1, 2] กับ [−2, −4] ได้ cos = **−1** (ทิศตรงข้าม)

**1.4 กลับโจทย์ หาค่าที่ไม่รู้ (ตั้งฉาก)** หา x ให้ u = [2, 3] ตั้งฉากกับ v = [x, 4]

1. ตั้งฉาก ⇒ cos = 0 ⇒ u·v = 0
2. 2x + 3×4 = 0 ⇒ 2x = −12 ⇒ x = −6
3. ตรวจ: u·v = 2(−6) + 12 = 0 ✓.
- ตอบ **x = −6**

**1.5 dot กับ cosine สลับไปมา**

- (ก) ‖u‖ = 10, ‖v‖ = 8, cos = 0.9 ⇒ u·v = 10 × 8 × 0.9 = **72**
- (ข) กลับโจทย์: u·v = 36, ‖u‖ = 5, ‖v‖ = 12 ⇒ cos = 36 / (5×12) = 36/60 = **0.6**
- กับดัก: ลืมคูณหรือหารด้วย ‖u‖‖v‖ ตรวจ: ผลของ (ข) ต้องอยู่ใน [−1, 1] (ถ้าได้ 7.2 แปลว่าคำนวณผิด)

### ประเภท 2: จัดอันดับเมื่อเวกเตอร์ไม่ได้ normalize (cosine, dot, L2 ให้อันดับต่างกัน)

สูตร: ใช้ cosine, dot, L2 distance จากสไลด์ 10 อันดับ 1 ของ cosine และ dot คือค่ามากสุด ส่วน L2 คือค่าน้อยสุด

**2.1** q = [1, 2], a = [2, 4], b = [3, 1], c = [0.5, 1.2]

| doc | cosine | dot | L2 |
|---|---|---|---|
| a | 1.0000 | 10 | √5 = 2.2361 |
| b | 0.7071 | 5 | √5 = 2.2361 |
| c | 0.9976 | 2.9 | 0.9434 |

- วิธีทำ a: dot = 2 + 8 = 10, ‖a‖ = √20, ‖q‖ = √5, cos = 10 / (√5·√20) = 10/10 = 1; L2 = ‖[−1, −2]‖ = √5
- วิธีทำ c: dot = 0.5 + 2.4 = 2.9, ‖c‖ = √1.69 = 1.3, cos = 2.9 / (2.2361 × 1.3) = 0.9976, L2 = ‖[0.5, 0.8]‖ = √0.89 = 0.9434
- อันดับ 1: cosine → **a**, dot → **a**, L2 → **c** (ต่ำสุด) และ L2 ของ a กับ b เท่ากัน (เสมอ) ทั้งที่ b คนละทิศ
- ตอบ: สามเมตริกไม่เห็นตรงกัน เพราะ dot และ L2 ถูกขนาดครอบงำ

**2.2** q = [5, 12], a = [10, 24], b = [12, 5], c = [2.5, 6]

- cosine: a = 1.0000, c = 1.0000 (ทั้งคู่ทิศเดียวกับ q), b = 60+60 / (13×13) = 120/169 = 0.7101
- dot: a = 50 + 288 = 338, b = 120, c = 12.5 + 72 = 84.5
- L2: a = ‖[−5, −12]‖ = 13, b = ‖[−7, 7]‖ = 9.8995, c = ‖[2.5, 6]‖ = 6.5
- อันดับ 1: cosine → a และ c เสมอ, dot → **a**, L2 → **c** บทเรียน: เวกเตอร์ที่ยาวกว่าชนะ dot, เวกเตอร์ที่ใกล้ในพิกัดชนะ L2

**2.3 หลัง normalize ทุกเมตริกเห็นตรงกัน** q = [3, 4], d₁ = [1.5, 2], d₂ = [4, 3] (ตัวอย่างหัวข้อ 3)

1. normalize: q → [0.6, 0.8], d₁ → [0.6, 0.8] (ยาว 2.5 หาร 2.5), d₂ → [0.8, 0.6]
2. dot: d₁ = 0.36 + 0.64 = 1.00, d₂ = 0.48 + 0.48 = 0.96
3. L2²: d₁ = 0, d₂ = 0.04 + 0.04 = 0.08 (ตรงกับ 2 − 2×0.96 = 0.08 ต่อยอดจากสไลด์)
- ตอบ ทั้ง dot, cosine, L2 ชี้ว่า **d₁** อันดับ 1 เหมือนกัน

**2.4 ทิศเดียวกันแต่ความยาวต่างกัน (เลือกเมตริกตามงาน)** u = [0.6, 0.8] (ยาว 1) และ v = [6, 8] (ยาว 10)

1. cosine = (3.6 + 6.4) / (1 × 10) = 10/10 = 1
2. dot = 0.6×6 + 0.8×8 = 10
3. L2 = ‖[5.4, 7.2]‖ = √(29.16 + 51.84) = √81 = 9
- ตอบ cosine = **1** (ทิศเดียวกัน) แต่ dot = **10** และ L2 = **9** (ไม่ใช่ 0) เพราะสองตัวหลังสนขนาด จึง semantic search ใช้ cosine ส่วน anomaly detection ใช้ L2 (ระยะสัมบูรณ์สำคัญ) ตามสไลด์ 42

### ประเภท 3: L2-normalize และตรวจ norm

สูตร: `v' = v / ‖v‖₂` หลัง normalize ‖v'‖ = 1

**3.1** v = [3, 4] ⇒ ‖v‖ = 5 ⇒ v' = [3/5, 4/5] = **[0.6, 0.8]** ตรวจ: 0.36 + 0.64 = 1

**3.2** v = [1, 2, 2] ⇒ ‖v‖ = 3 ⇒ v' = [0.3333, 0.6667, 0.6667] ตรวจ: 0.1111 + 0.4444 + 0.4444 = 1

**3.3 dot ของสองเวกเตอร์ที่ normalize แล้ว** a = [3, 4], b = [5, 12]

1. a' = [0.6, 0.8], b' = [5/13, 12/13] = [0.3846, 0.9231]
2. a'·b' = 0.2308 + 0.7385 = 0.9692
3. ตรวจ: cos(a, b) ตรง ๆ = (15+48)/(5×13) = 63/65 = 0.9692 ✓.
- ตอบ **0.9692** (dot หลัง normalize = cosine)

**3.4 กับดักทศนิยมจากเดโม** ก่อน normalize ค่าตัวแรกของเวกเตอร์แรกคือ −0.1818 และ ‖v‖ = 10.2098

1. ค่าใหม่ = −0.1818 / 10.2098 = −0.017807
- ตอบ **−0.0178** (เดโมพิมพ์ −0.017807) ไม่ใช่ −0.178 (คลาดเลขยกกำลัง 10) ตรวจ: norm เดิมประมาณ 10 และต้องเหลือ 1 ทุกค่าจึงหดลงราว 10 เท่า (ต่อยอดจากสไลด์: ถ้าทั้ง 768 มิติมีขนาดเท่ากัน แต่ละมิติจะเป็น 1/√768 = 0.0361)

**3.5 กลับโจทย์** เวกเตอร์ unit [0.6, x] โดย x > 0 ⇒ 0.36 + x² = 1 ⇒ x² = 0.64 ⇒ x = **0.8**

### ประเภท 4: Cosine distance, L2 และการแปลงค่า D ของ FAISS

สูตร: cosine distance = 1 − cos; เมื่อเป็น unit vector `‖u−v‖² = 2 − 2cos` (ต่อยอดจากสไลด์; พิสูจน์อยู่หัวข้อ 3) ใช้แปลงค่า D ที่ `IndexFlatL2` หรือ `IndexHNSWFlat` (ค่าเริ่มต้น L2) คืนมา ซึ่งเป็นระยะกำลังสอง

**4.1** cos = 0.96 ⇒ cosine distance = 1 − 0.96 = **0.04**; ‖u−v‖² = 2 − 1.92 = **0.08**; ‖u−v‖ = √0.08 = **0.2828**

**4.2 cosine ติดลบ** cos = −0.3 ⇒ cosine distance = 1 − (−0.3) = **1.3** (ไม่ใช่ 0.7); ‖u−v‖² = 2 + 0.6 = **2.6** ตรวจ: cosine distance ต้องอยู่ใน [0, 2]

**4.3 แปลง D กลับเป็น cosine** (ต่อยอดจากสไลด์) vectors ถูก normalize แล้ว

- D = 0.5 ⇒ cos = 1 − 0.5/2 = **0.75**
- D = 1.6 ⇒ cos = 1 − 0.8 = **0.2**
- D = 0.08 ⇒ cos = 1 − 0.04 = **0.96**
- กับดัก: ถ้า D เป็นระยะกำลังสอง ห้ามยกกำลังสองซ้ำ และ D ต่ำ = ใกล้ (กลับกับคะแนน IP)

**4.4 รวมสองขั้นตอนจากเดโม** "eating food" กับ "eating pasta" ได้ cos = 0.7035

1. cosine distance = 1 − 0.7035 = **0.2965**
2. ‖u−v‖² = 2 − 2(0.7035) = 2 − 1.407 = **0.593** ⇒ ‖u−v‖ = √0.593 = **0.7701**
3. กับ "eating food" เทียบ "carrying a baby" cos = −0.1050 ⇒ cosine distance = 1.105

### ประเภท 5: นับคู่และเวลาของ cross-encoder เทียบ bi-encoder

สูตร: จำนวนคู่ `n(n−1)/2`, เวลา cross = จำนวนคู่ × เวลาต่อ forward, เวลา encode ของ bi = n × เวลาต่อ forward (สไลด์ 7-8)

**5.1 นับคู่** n = 100 ⇒ 100 × 99 / 2 = **4,950** คู่; n = 12 (เดโม) ⇒ 12 × 11 / 2 = **66** คู่ กับดัก: ใช้ n² = 10,000

**5.2 เปลี่ยนสเกล** n = 20,000, 5 ms ต่อ forward

1. คู่ = 20,000 × 19,999 / 2 = 199,990,000 ≈ 2.0 × 10⁸
2. เวลา = 199,990,000 × 5 ms = 999,950,000 ms = 999,950 s
3. ชั่วโมง = 999,950 / 3,600 = 277.8 h; วัน = 277.8 / 24 = 11.57 วัน
4. bi-encoder (ส่วน encode) = 20,000 × 5 ms = 100,000 ms = **100 s**
- ตอบ cross-encoder ≈ **277.8 ชั่วโมง (11.6 วัน)** เทียบ bi-encoder 100 วินาที อัตราส่วน = 999,950 / 100 = **9,999.5 เท่า** ตรวจ: n ใหญ่ขึ้น 2 เท่า เวลา cross ควรโตราว 4 เท่า (69.4 h → 277.8 h ✓)

**5.3 เปลี่ยนหน่วยเวลาต่อ forward** n = 5,000, 2 ms

1. คู่ = 5,000 × 4,999 / 2 = 12,497,500
2. เวลา = 12,497,500 × 2 ms = 24,995,000 ms = 24,995 s
3. = 24,995 / 60 = 416.6 นาที = 416.6 / 60 = **6.94 ชั่วโมง**
- กับดัก: 2 ms = 0.002 s (ไม่ใช่ 0.02 s) ถ้าคลาดจะได้ 69.4 ชั่วโมง

**5.4 กลับโจทย์ หา n** (ก) มีคู่ 4,950 คู่ ⇒ n(n−1)/2 = 4,950 ⇒ n(n−1) = 9,900 ⇒ n = **100** (100 × 99 = 9,900 ✓.)
(ข) งบเวลา 8 ชั่วโมง ที่ 5 ms ต่อคู่

1. 8 ชั่วโมง = 28,800 s = 28,800,000 ms
2. คู่สูงสุด = 28,800,000 / 5 = 5,760,000
3. n(n−1)/2 ≤ 5,760,000 ⇒ n(n−1) ≤ 11,520,000 ⇒ n ≈ 3,394.6
4. ตรวจ n = 3,394: 5,757,921 คู่ = 28,789.6 s = 7.997 h ✓. n = 3,395: 5,761,315 คู่ = 28,806.6 s = 8.0018 h เกิน
- ตอบ **n ≤ 3,394 ประโยค**

**5.5 รวมสองขั้นตอน (ตั๋ว 100,000 ใบ ตามกิจกรรมสไลด์ 25)** 5 ms ต่อ forward

1. คู่ = 100,000 × 99,999 / 2 = 4,999,950,000 ≈ 5.0 × 10⁹
2. cross-encoder = 4,999,950,000 × 5 ms = 24,999,750,000 ms = 24,999,750 s = **6,944.4 h ≈ 289.3 วัน**
3. bi-encoder encode = 100,000 × 5 ms = 500,000 ms = 500 s = **8.33 นาที**
- ตรวจ: อัตราส่วน = (n−1)/2 = 49,999.5 เท่า เมื่อเวลาต่อ forward เท่ากัน

### ประเภท 6: Retrieve-then-Rerank (ต่อยอดจากสไลด์ 18)

สูตร: เวลาต่อ query ของระบบสองขั้น = เวลา encode query + เวลา search + k × เวลา cross-encoder ต่อคู่ (เวกเตอร์เอกสาร encode ไว้ล่วงหน้า) ระบบที่ใช้ cross-encoder ทุกเอกสาร = N × เวลาต่อคู่

**6.1** (ตัวอย่างพื้นฐานอยู่ในโจทย์ตัวอย่าง 3) N = 1,000,000, cross 5 ms, encode query 5 ms, search 2 ms, rerank top-100 ⇒ ระบบสองขั้น = 5 + 2 + 100 × 5 = 507 ms เทียบ 5,000,000 ms ได้ 9,861.9 เท่า

**6.2 เปลี่ยนตัวเลข** N = 500,000, cross 4 ms, encode 8 ms, search 3 ms, rerank top-50

1. ระบบ A = 500,000 × 4 = 2,000,000 ms = 2,000 s = 33.3 นาที
2. ระบบ B = 8 + 3 + 50 × 4 = 211 ms
3. อัตราส่วน = 2,000,000 / 211 = **9,478.7 ≈ 9,479 เท่า**

**6.3 เปลี่ยนจำนวน k** ใช้ข้อมูลของ 6.1 แต่ rerank แค่ top-20

- B = 5 + 2 + 20 × 5 = 107 ms ⇒ อัตราส่วน = 5,000,000 / 107 = **46,729 เท่า** (4.67 × 10⁴)
- ข้อสังเกต: k น้อยลงทำให้เร็วขึ้น แต่ถ้าเอกสารที่ถูกต้องอยู่นอก top-20 cross-encoder ไม่เห็นเลย Recall@20 คือเพดานของระบบ

**6.4 กลับโจทย์ หา k สูงสุด** งบรวม 100 ms ต่อ query, encode 5 ms, search 2 ms, cross 5 ms ต่อคู่

1. 5 + 2 + 5k ≤ 100 ⇒ 5k ≤ 93 ⇒ k ≤ 18.6
2. ตรวจ k = 18 ⇒ 5 + 2 + 90 = 97 ms ✓. k = 19 ⇒ 102 ms เกิน
- ตอบ **k = 18** (ปัดลง ไม่ปัดขึ้น)

### ประเภท 7: มิติของ tensor และจำนวนพารามิเตอร์ของ head

สูตร: `c = [u; v; |u−v|]` มี 3d มิติ, W ขนาด (3d) × K, logits `[B, K]`

**7.1 เปลี่ยน d** d = 512 ⇒ c = 3 × 512 = **1,536** มิติ; W = 1,536 × 3 = **4,608** ตัว (บวก bias 3 ตัวเป็น 4,611) กับดัก: 1,536 เท่ากับ 2 × 768 (กรณี `[u; v]` ของ BERT-base) บังเอิญ ต้องดูว่าโจทย์ให้ d เท่าไร

**7.2 กลับโจทย์ หา d** c มี 3,072 มิติ ⇒ d = 3,072 / 3 = **1,024** (bge-large) และ c = 1,152 ⇒ d = **384** (MiniLM)

**7.3 เปลี่ยนจำนวน label** d = 768, K = 5 ⇒ W = 2,304 × 5 = **11,520** ตัว; batch B = 32 ⇒ c ∈ `[32, 2304]`, logits ∈ `[32, 5]` (NLI ที่ K = 3 ได้ `[32, 3]`)

**7.4 กลับโจทย์จากจำนวนพารามิเตอร์** W มี 6,912 ตัว และ K = 3 ⇒ 3d = 6,912 / 3 = 2,304 ⇒ d = **768**

**7.5 นับจำนวนค่าใน tensor (ต่อยอดจากสไลด์)** B = 16, T = 128 (max seq สไลด์ 33), d = 768

1. H ∈ `[16, 128, 768]` มี 16 × 128 × 768 = 1,572,864 ค่า = 1,572,864 × 4 = 6,291,456 ไบต์ ≈ 6.29 MB
2. หลัง pooling `[16, 768]` = 12,288 ค่า และ c = `[16, 2304]` = 36,864 ค่า
- ตรวจ: pooling ลดแกนความยาว T ทิ้งทั้งแกน (128 → หายไป)

### ประเภท 8: Pooling (mean แบบมี mask, CLS, max)

สูตร: `s = Σ Hₜ·mₜ / Σ mₜ`, CLS: `s = H₀`, max: `sᵢ = maxₜ Hₜ,ᵢ`

**8.1** d = 2, แถวจริง H₁ = [1, 2], H₂ = [3, 4], H₃ = [5, 9], แถว `[PAD]` H₄ = [100, 100], mask = [1, 1, 1, 0]

1. Σ Hₜ·mₜ = [1+3+5, 2+4+9] = [9, 15]
2. Σ mₜ = 3
3. masked mean = [9/3, 15/3] = **[3, 5]**
- เทียบ: ไม่ใช้ mask = [109, 115]/4 = [27.25, 28.75] (ถูก `[PAD]` ลาก); CLS = H₀ = [1, 2] (แถวแรก); max (นับเฉพาะแถวจริง) = [5, 9]; max ถ้ารวม PAD = [100, 100]
- กับดัก: หารด้วย T = 4 แทน Σ m = 3 (ได้ [2.25, 3.75] ผิด)

**8.2 สามมิติ** แถวจริง [0.5, 1.0, 2.0], [1.5, 3.0, 0.0], [2.5, 2.0, 1.0] และแถว PAD อีก 2 แถว [9, 9, 9] mask = [1, 1, 1, 0, 0]

- masked mean = [4.5, 6.0, 3.0] / 3 = **[1.5, 2.0, 1.0]**
- max = [2.5, 3.0, 2.0]; CLS = [0.5, 1.0, 2.0]
- ไม่ใช้ mask: ผลรวมแต่ละมิติ = [22.5, 24.0, 21.0] หาร 5 = [4.5, 4.8, 4.2] ซึ่งเพี้ยนมาก

**8.3 กลับโจทย์ หา token ที่หายไป** ประโยคมี token จริง 3 ตัว mean = [2, 3] และรู้สอง token คือ [1, 2] กับ [4, 5]

1. ผลรวมของสามตัว = 3 × [2, 3] = [6, 9]
2. token ที่สาม = [6, 9] − ([1, 2] + [4, 5]) = [6, 9] − [5, 7] = **[1, 2]**

**8.4 T ไม่เท่ากับ Σ m** ประโยคยาว T = 6 แต่ mask = [1, 1, 1, 1, 0, 0] แถวจริง [2, 0], [4, 2], [6, 4], [8, 10] และ PAD [50, 50] สองแถว

- masked: ผลรวม [20, 16] / 4 = **[5, 4]**
- ไม่มี mask: (ผลรวม [20, 16] + [100, 100]) / 6 = [120, 116]/6 = [20, 19.33] (ผิด)

**8.5 ตัวหารผิด** ผลรวมของ token จริงในมิติหนึ่ง = 45.0 ประโยคจากเดโมมี T = 10 โดย mask มีค่า 1 จำนวน 9 ตัว และ 0 จำนวน 1 ตัว

- หารถูก: 45.0 / Σ m = 45.0 / 9 = **5.0**
- หารด้วย T = 10 ได้ 4.5 ซึ่งต่ำกว่าค่าจริง 10%
- ข้อนี้ยังมองโลกในแง่ดีเพราะสมมุติให้ PAD บวกเข้ามาเป็นศูนย์ แต่เดโมวัดว่าเวกเตอร์ `[PAD]` มี norm เฉลี่ย 9.67 ไม่ใกล้ศูนย์ ถ้าไม่ใช้ mask ค่าที่บวกเข้ามาจึงบิดเบือนมากกว่านี้

### ประเภท 9: Triplet loss (คำนวณตรง ๆ)

สูตร: `L = max(0, d(a,p) − d(a,n) + α)`

**9.1 Euclidean สามมิติ** a = (0,0,0), p = (1,2,2), n = (2,3,6), α = 1.0

1. d(a,p) = √(1+4+4) = 3
2. d(a,n) = √(4+9+36) = √49 = 7
3. L = max(0, 3 − 7 + 1) = max(0, −3) = **0** (easy: 3 + 1 = 4 ≤ 7)

**9.2 margin ใหญ่ขึ้นทำให้ loss กลับมา** a = (1,1), p = (1,2), n = (4,5)

1. d(a,p) = 1, d(a,n) = √(9+16) = 5
2. α = 0.5: L = 1 − 5 + 0.5 = −3.5 ⇒ **0**
3. α = 4.5: L = 1 − 5 + 4.5 = **0.5** (margin 4.5 มากกว่าช่องว่างของระยะ 4)

**9.3 cosine distance เทียบ Euclidean** a = [1, 0], p = [0.6, 0.8], n = [0.8, 0.6], α = 0.5

1. cosine distance: cos(a,p) = 0.6 ⇒ d = 0.4; cos(a,n) = 0.8 ⇒ d = 0.2; L = 0.4 − 0.2 + 0.5 = **0.7**
2. Euclidean: d(a,p) = √(0.16+0.64) = 0.8944; d(a,n) = √(0.04+0.36) = 0.6325; L = 0.8944 − 0.6325 + 0.5 = **0.7620**
- สรุป: n อยู่ใกล้ a กว่า p (hard negative) loss > 0 ทั้งสองแบบ แต่ค่าต่างกัน เพราะ metric เป็นส่วนของ loss

**9.4 d(a,n) = d(a,p)** a = (0.2, 0.4), p = (0.5, 0.8), n = (0.5, 0.0), α = 0.5

1. d(a,p) = √(0.09+0.16) = 0.5; d(a,n) = √(0.09+0.16) = 0.5
2. L = 0.5 − 0.5 + 0.5 = **0.5** (เท่ากับ α พอดี เมื่อ negative ห่างเท่ากับ positive)

**9.5 กับดักทศนิยมและเครื่องหมาย** d(a,p) = 0.25, d(a,n) = 0.90, α = 0.6

- 0.25 − 0.90 + 0.6 = −0.05 ⇒ L = max(0, −0.05) = **0** (ไม่ใช่ 0.05)
- ตรวจ: d(a,p) + α = 0.85 ≤ 0.90 ✓.

### ประเภท 10: Triplet loss กลับโจทย์ และชนิดของ negative

**10.1 หา d(a,n) ต่ำสุดที่ทำให้ loss = 0** d(a,p) = 0.3, α = 0.5 ⇒ ต้อง d(a,n) ≥ 0.3 + 0.5 = **0.8**; ถ้า d(a,p) = 0.12, α = 0.8 ⇒ d(a,n) ≥ **0.92**

**10.2 หา α** L = 0.35, d(a,p) = 0.4, d(a,n) = 0.6 ⇒ 0.35 = 0.4 − 0.6 + α ⇒ α = 0.35 + 0.2 = **0.55**

**10.3 หา d(a,p)** L = 0.45 (> 0), d(a,n) = 0.9, α = 0.5 ⇒ 0.45 = d(a,p) − 0.9 + 0.5 ⇒ d(a,p) = 0.45 + 0.4 = **0.85** (ใช้ได้เฉพาะเมื่อ L > 0 เพราะ max ตัด loss ที่ติดลบทิ้ง)

**10.4 จำแนก negative** d(a,p) = 0.2, α = 0.6 ⇒ ช่วง semi-hard คือ 0.2 < d(a,n) < 0.8

| d(a,n) | ชนิด | L = 0.2 − d(a,n) + 0.6 |
|---|---|---|
| 0.1 | hard (d(a,n) < d(a,p)) | 0.7 |
| 0.5 | semi-hard | 0.3 |
| 0.8 | ขอบ (zero-loss ใช้ ≤ แต่ semi-hard ใช้ <) | 0 |
| 1.0 | easy | max(0, −0.2) = 0 |

### ประเภท 11: Margin ranking loss

สูตร: `L = max(0, sim(a,n) − sim(a,p) + α)` และ d = 1 − sim ทำให้เท่ากับ triplet

**11.1** sim(a,p) = 0.9, sim(a,n) = 0.3, α = 0.5 ⇒ 0.3 − 0.9 + 0.5 = −0.1 ⇒ **0** แปลงเป็น triplet (d = 1 − sim): d(a,p) = 0.1, d(a,n) = 0.7 ⇒ L = 0.1 − 0.7 + 0.5 = −0.1 ⇒ **0** ตรงกัน เพราะเทอม 1 ตัดกัน

**11.2 กับดักทศนิยม** sim(a,p) = 0.6, sim(a,n) = 0.55, α = 0.2 ⇒ 0.55 − 0.6 + 0.2 = **0.15** (ไม่ใช่ 1.5)

**11.3 จากเวกเตอร์** a = [2, 0], p = [3, 1], n = [1, 3], α = 0.4

1. cos(a,p) = 6 / (2 × √10) = 0.9487
2. cos(a,n) = 2 / (2 × √10) = 0.3162
3. L = 0.3162 − 0.9487 + 0.4 = −0.2325 ⇒ **0**

**11.4 กลับโจทย์ หา sim(a,n) สูงสุด** sim(a,p) = 0.82, α = 0.3 ⇒ ต้อง sim(a,n) − 0.82 + 0.3 ≤ 0 ⇒ sim(a,n) ≤ **0.52**; ถ้า sim(a,n) = 0.6 ⇒ L = 0.6 − 0.82 + 0.3 = **0.08**

**11.5 กับดักเครื่องหมาย** sim(a,p) = 0.8, sim(a,n) = 0.9 (negative คล้ายกว่า positive), α = 0.5

- ที่ถูก: 0.9 − 0.8 + 0.5 = **0.6**; ถ้าสลับเป็น 0.8 − 0.9 + 0.5 = 0.4 ผิด (ลำดับของ sim สลับกับ triplet)

### ประเภท 12: MNRL / InfoNCE

สูตร: `Lᵢ = −log [ exp(sim(qᵢ,pᵢ)/τ) / Σⱼ exp(sim(qᵢ,pⱼ)/τ) ]` (log เป็นลอการิทึมธรรมชาติ ln)

**12.1 นับ negative และขนาดตาราง** N = 64 ⇒ negative ต่อ query = **63**, ตาราง 64 × 64 = **4,096** ช่อง (positive 64 ช่องบนแนวทแยง, negative 4,032 ช่อง); N = 256 ⇒ 255 negative ต่อ query, ตาราง 65,536 ช่อง, negative ทั้งตาราง 65,280 ช่อง (N(N−1)) กับดัก: ตอบ N แทน N − 1

**12.2 คำนวณ loss** sim ของ query หนึ่งกับ p ทั้งสาม = [0.9 (positive), 0.7, 0.1], τ = 0.1

1. sim/τ = [9, 7, 1]
2. exp = [8,103.08, 1,096.63, 2.718]; ผลรวม = 9,202.44
3. P(positive) = 8,103.08 / 9,202.44 = 0.8805
4. L = −ln 0.8805 = **0.1272**
- เปลี่ยน τ: τ = 0.5 ⇒ logit [1.8, 1.4, 0.2] ⇒ exp [6.0496, 4.0552, 1.2214] ผลรวม 11.3263 ⇒ P = 0.5341 ⇒ L = **0.6271**; τ = 1 ⇒ exp [2.4596, 2.0138, 1.1052] ผลรวม 5.5786 ⇒ P = 0.4409 ⇒ L = **0.8189**
- สรุป: τ ต่ำ ⇒ softmax คมขึ้น ⇒ loss ของ positive ที่ชนะอยู่แล้วต่ำลง ตรวจ: P ต้องอยู่ใน [0, 1]

**12.3 กรณีเริ่มต้นสุ่มเท่ากัน (ต่อยอดจากสไลด์)** ถ้าทุก sim เท่ากัน P = 1/N ⇒ L = ln N: N = 4 ⇒ **1.3863**; N = 256 ⇒ **5.5452** ใช้เป็นเกณฑ์ตรวจว่า loss เริ่มต้นสมเหตุสมผล

**12.4 กลับโจทย์ หา P จาก loss** L = 0.6931 ⇒ P = e^(−0.6931) = **0.5**; L = 2.3026 ⇒ P = **0.1** (ln 10 = 2.3026)

**12.5 negative ที่ยากทำให้ loss ต่างกันตาม τ** มี positive sim = 0.5 และ negative เดียว sim = 0.6 (negative คล้ายกว่า)

- τ = 0.1: logit [5, 6] ⇒ P = 1/(1 + e) = 0.2689 ⇒ L = **1.3133**
- τ = 0.05: logit [10, 12] ⇒ P = 1/(1 + e²) = 0.1192 ⇒ L = **2.1269**
- สรุป: τ ต่ำลงลงโทษ hard negative แรงขึ้น

### ประเภท 13: Softmax cross-entropy ของ classification head (NLI)

สูตร: `p = softmax(logits)`, `L = −ln p_y` (สไลด์ 17 และ 22 ใช้ softmax กับ CrossEntropy)

**13.1** logits = [2.0, 1.0, 0.0], label คือคลาสแรก (entailment)

1. exp = [7.3891, 2.7183, 1.0000] ผลรวม = 11.1073
2. p = [0.6652, 0.2447, 0.0900]
3. L = −ln 0.6652 = **0.4076**

**13.2 label เปลี่ยน** logits เดิม แต่ label คือคลาสที่สาม (contradiction) ⇒ p = 0.0900 ⇒ L = −ln 0.0900 = **2.4076** (ทำนายผิดคลาส loss สูง)

**13.3 ไม่รู้อะไรเลย (ต่อยอดจากสไลด์)** logits เท่ากันหมด ⇒ p = 1/K ⇒ L = ln K: K = 3 ⇒ **1.0986**; K = 2 ⇒ **0.6931**

**13.4** logits = [0.5, 2.5, 0.5], label = neutral (คลาสกลาง) ⇒ exp = [1.6487, 12.1825, 1.6487] ผลรวม = 15.4799 ⇒ p = 0.7870 ⇒ L = **0.2395**

### ประเภท 14: MSE ของ regression (STS) และการ normalize label

สูตร: label 0-5 หารด้วย 5 ให้เป็น [0, 1], `ℒ = mean((ŝ − s)²)` โดย ŝ = cos(u,v)

**14.1** ŝ = [0.9, 0.5, 0.1], s = [1.0, 0.6, 0.0] ⇒ error = [−0.1, −0.1, 0.1] ⇒ กำลังสอง [0.01, 0.01, 0.01] ⇒ MSE = 0.03 / 3 = **0.01**

**14.2 normalize label** คะแนนดิบ 3.8, 2.5, 0.6, 4.4 หารด้วย 5 ⇒ **0.76, 0.50, 0.12, 0.88** กับดัก: หารด้วย 4 หรือหารด้วย 100

**14.3 กับดักทศนิยม** ŝ = [0.7, 0.1, 0.4, 0.9], s = [0.8, 0.2, 0.4, 1.0] ⇒ error = [−0.1, −0.1, 0, −0.1] ⇒ กำลังสองรวม 0.03 ⇒ MSE = 0.03/4 = **0.0075** (ไม่ใช่ 0.075)

**14.4 ถ้าไม่ normalize** label ดิบ [3.0, 2.0, 0.5, 0.0] cos ทำได้มากสุด 1 ⇒ ค่าที่ใกล้ที่สุดคือ [1, 1, 0.5, 0] ⇒ error² = [4, 1, 0, 0] ⇒ MSE ต่ำสุด = 5/4 = **1.25** (ไม่ถึง 0 ตลอดไป)

**14.5 กลับโจทย์** MSE = 0.02 ใน 2 คู่ โดยคู่แรก error = 0.1 ⇒ error² รวม = 0.04 ⇒ คู่ที่สอง error² = 0.04 − 0.01 = 0.03 ⇒ |error| = √0.03 = **0.1732**

### ประเภท 15: Recall@k และ precision@k

สูตร: `Recall@k = |Retrieved_k ∩ Relevant| / |Relevant|`, precision@k = ตัวเดียวกันหารด้วย k (ต่อยอดจากสไลด์)

**15.1** |Relevant| = 5, พบใน top-10 จำนวน 2 ⇒ Recall@10 = 2/5 = **0.4**; precision@10 = 2/10 = 0.2

**15.2 k น้อยกว่า |Relevant|** |Relevant| = 8, top-5 มีที่เกี่ยวข้องครบ 5 ⇒ Recall@5 = 5/8 = **0.625**; precision@5 = 5/5 = 1.0 ข้อสังเกต: Recall@3 สูงสุดที่เป็นไปได้ = 3/8 = 0.375

**15.3 ใช้ตรวจ ANN (ต่อยอดจากสไลด์ 37)** ถือผล exact top-10 เป็น relevant (10 ฉบับ) ANN คืนมา 10 ฉบับ ตรงกับ exact 9 ฉบับ ⇒ Recall@10 = 9/10 = **0.9** ซึ่งตรงกับระดับ ~90% ของ IVF+PQ ในตารางสไลด์ 39

**15.4 กลับโจทย์** Recall@k = 0.75, |Relevant| = 12 ⇒ พบ = 0.75 × 12 = **9 ฉบับ**

### ประเภท 16: MRR

สูตร: `MRR = (1/|Q|) Σ 1/rankᵢ` ใช้อันดับของเอกสารถูกต้อง **อันแรก** ของแต่ละ query

**16.1** อันดับแรกของ 4 query = 1, 3, 2, 5 ⇒ 1 + 0.3333 + 0.5 + 0.2 = 2.0333 ⇒ MRR = 2.0333/4 = **0.5083**

**16.2** อันดับ = 2, 2, 4 ⇒ 0.5 + 0.5 + 0.25 = 1.25 ⇒ MRR = 1.25/3 = **0.4167**

**16.3 มี query ที่หาไม่เจอ (ต่อยอดจากสไลด์)** อันดับ = 1, ไม่เจอ, 2 ⇒ (1 + 0 + 0.5)/3 = **0.5**

**16.4 กลับโจทย์** MRR = 0.45 จาก 4 query; สาม query อันดับ 1, 2, 5 หา query ที่สี่

1. ผลรวม reciprocal = 4 × 0.45 = 1.8
2. สามตัวแรก = 1 + 0.5 + 0.2 = 1.7
3. ตัวที่สี่ = 1.8 − 1.7 = 0.1 ⇒ rank = 1/0.1 = **10**

**16.5 กับดักค่าเฉลี่ยอันดับ** อันดับ = 1, 1, 10, 4, 2 ⇒ reciprocal = 1 + 1 + 0.1 + 0.25 + 0.5 = 2.85 ⇒ MRR = 2.85/5 = **0.57** วิธีผิด: เฉลี่ยอันดับก่อน (18/5 = 3.6) แล้วกลับเป็น 1/3.6 = 0.2778 ไม่ใช่ MRR

### ประเภท 17: หน่วยความจำของเวกเตอร์ (GB เทียบ GiB, float32 เทียบ float64)

สูตร: ไบต์ = n × d × b, โดย b = 4 (float32) หรือ 8 (float64) 1 GB = 10⁹ ไบต์, 1 GiB = 2³⁰ = 1,073,741,824 ไบต์

**17.2 เปลี่ยนสเกล** n = 50,000,000, d = 384 ⇒ 50,000,000 × 384 × 4 = 76,800,000,000 ไบต์ = **76.8 GB** = 71.53 GiB (เกิน RAM 32 GB ต้องใช้ index แบบบีบอัด)

**17.3 float64** n = 10,000,000, d = 768 ใช้ float64 ⇒ 10,000,000 × 768 × 8 = 61,440,000,000 ไบต์ = **61.44 GB** (57.22 GiB) เท่ากับ float32 ที่ 20M เวกเตอร์ และ FAISS ต้องการ float32 (สไลด์ 41)

**17.4 กลับโจทย์ หา n สูงสุด** RAM 32 GB (1 GB = 10⁹), d = 768, float32

1. ไบต์ต่อเวกเตอร์ = 768 × 4 = 3,072
2. n = 32 × 10⁹ / 3,072 = 10,416,666 ≈ **10.4 ล้านเวกเตอร์** (ถ้านับ 32 GiB จะได้ 11,184,810)
3. ในทางปฏิบัติต้องเหลือที่ให้ระบบและ index จึงน้อยกว่านี้ และ 5M ใช้ 15.36 GB (48% ของ RAM) ยังพอ

**17.5 กลับโจทย์ หา d** เวกเตอร์ 1,000,000 ตัว ใช้ 3.072 GB (float32) ⇒ d = 3.072 × 10⁹ / (10⁶ × 4) = **768** ไบต์ต่อเวกเตอร์ของ d = 384 คือ 1,536 ไบต์ และของ d = 1,024 คือ 4,096 ไบต์

### ประเภท 18: เวลา brute-force ต่อ query และ ANN

สูตร: เวลา ≈ n × d / 10⁹ วินาที (ที่ 1 GHz, สไลด์ 36) ANN เร็วขึ้นราว 100 เท่าที่ recall 99%+

**18.1** n = 1,000,000, d = 1,024 ⇒ 1.024 × 10⁹ / 10⁹ = **1.024 s**

**18.2 รวมสองขั้นตอน** n = 50,000,000, d = 384

1. n × d = 1.92 × 10¹⁰ ⇒ brute-force = **19.2 s**
2. ANN เร็วขึ้น 100 เท่า = 19.2 / 100 = 0.192 s = **192 ms**
- กับดัก: ใช้ d = 768 แทน 384 จะได้ 38.4 s

**18.3 กลับโจทย์ หา n ที่ทำได้ใน 50 ms** d = 768, 1 GHz

1. n × 768 / 10⁹ ≤ 0.05 s ⇒ n ≤ 0.05 × 10⁹ / 768 = 65,104
- ตอบ **n ≈ 65,000 เวกเตอร์** สอดคล้องกับเกณฑ์ "Flat เหมาะกับ < 100K" ของสไลด์ 39

**18.4 เปลี่ยนความเร็วสัญญาณนาฬิกา** 10M × 768 ที่ 2 GHz ⇒ 7.68 × 10⁹ / (2 × 10⁹) = **3.84 s** (เร็วขึ้นเมื่อ GHz มากขึ้น)

**18.5 (ต่อยอดจากสไลด์) IVF ≈ O(√n·d)** n = 10,000,000, d = 768 ⇒ √n = 3,162 ⇒ 3,162 × 768 = 2.43 × 10⁶ ครั้ง ⇒ 2.43 ms ที่ 1 GHz เร็วกว่า brute-force ราว √n = 3,162 เท่าตามสูตร (ไม่รวมค่าคงที่ และ recall เหลือ ~95%) ใช้เทียบอันดับความเร็วเท่านั้น ไม่ใช่เวลาที่วัดจริง

### ประเภท 20: การเทรน SBERT (จำนวน step และเวลา)

สูตร: step ต่อ epoch = ⌈จำนวนคู่ / batch⌉ ข้อมูลจากสไลด์ 22-23, 33: NLI ≈ 1,000,000 คู่ (570K + 430K), STSb ≈ 8,500 คู่, batch 16, 1 epoch, ~20 นาที (NLI) + ~5 นาที (STS)

**20.2 เปลี่ยน batch** batch 32 ⇒ 1,000,000 / 32 = **31,250 step** (ครึ่งหนึ่งของ batch 16); batch 64 ⇒ **15,625 step**

**20.3 กลับโจทย์ หา batch** 1 epoch ของ NLI มี 31,250 step ⇒ batch = 1,000,000 / 31,250 = **32**

### ข้อความที่ผิดและเฉลยที่ถูก (สไตล์ "ข้อใดไม่ถูกต้อง")

อ่านคู่ละบรรทัด: ผิด คือตัวอย่างข้อความผิดที่เขียนขึ้นตามแบบตัวเลือกลวงของข้อสอบ (ไม่ใช่ข้อสอบจริง) ถูก คือข้อเท็จจริงที่ใช้ตัดสิน

1. ผิด: BERT ดิบให้ sentence embedding ดีเพราะเฉลี่ย token แล้วได้ภาพรวมของประโยค -> ถูก: BERT ดิบแพ้ GloVe average บน STS (mean pooling 46.35, `[CLS]` 16.50 เทียบ GloVe 58.02) (สไลด์ 4)
2. ผิด: anisotropy เกิดเพราะสถาปัตยกรรม self-attention หรือเพราะมิติ 768 เล็กเกินไป -> ถูก: สาเหตุคือ training objective (MLM) ไม่เคยบังคับให้ geometry ระดับประโยคดี (สไลด์ 9)
3. ผิด: anisotropy แปลว่า cosine ของทุกคู่เท่ากับประมาณ 0.99 -> ถูก: แปลว่าไม่มีคู่ใดได้ค่าต่ำ (raw BERT อยู่ใน [0.46, 0.85] เฉลี่ย 0.58) จึงไม่มีช่วงให้จัดอันดับ (สไลด์ 19, เดโม 2b)
4. ผิด: `[CLS]` ของ BERT ดิบจัดอันดับคู่ที่เกี่ยวข้องสูงกว่าคู่ที่ไม่เกี่ยวข้องเสมอ -> ถูก: เดโมสไลด์ 12 ให้คู่ไม่เกี่ยว 0.86 สูงกว่าคู่เกี่ยว 0.79 คืออันดับกลับด้าน (สไลด์ 12)
5. ผิด: ชั้นลึกของ BERT, ELMo, GPT-2 มี anisotropy น้อยกว่าชั้นตื้น -> ถูก: ชั้นสูงมักมี anisotropy มากกว่า มีข้อยกเว้นเช่นชั้นอินพุตของ ELMo (สไลด์ 5)
6. ผิด: Bi-encoder ต้องรัน BERT n² ครั้งเพื่อเทียบทุกคู่ -> ถูก: bi-encoder ใช้ n forward pass แล้วเทียบด้วย dot product ส่วน n(n−1)/2 forward pass คือของ cross-encoder (สไลด์ 7, 8)
7. ผิด: cross-encoder เหมาะดึงผู้สมัครรอบแรกจากหลายล้านเอกสารเพราะแม่นที่สุด -> ถูก: cross-encoder ใช้ rerank รอบสอง ส่วนรอบแรกใช้ bi-encoder (สไลด์ 18)
8. ผิด: Siamese network ใช้ BERT สองตัวที่ฝึกน้ำหนักแยกกัน -> ถูก: สาขาทั้งสองสถาปัตยกรรมเดียวกันและน้ำหนักเดียวกัน (weight sharing) (สไลด์ 13)
9. ผิด: mean pooling ของ SBERT เฉลี่ยทุกตำแหน่งรวม `[PAD]` ด้วย -> ถูก: ใช้ attention mask เฉลี่ยเฉพาะ token จริง ตัวหารคือ Σ mₜ (สไลด์ 15)
10. ผิด: เวกเตอร์ `[PAD]` มี norm ใกล้ศูนย์ เฉลี่ยรวมแล้วแค่ทำให้เวกเตอร์เล็กลง -> ถูก: เดโมวัด norm เฉลี่ยของ `[PAD]` = 9.67 (token จริง 14.90) การรวมเข้าไปบิดเบือนเวกเตอร์ (เดโม)
11. ผิด: SBERT แบบ classification ต่อ `[u; v]` เข้า softmax จึงได้เวกเตอร์ 1,536 มิติ -> ถูก: ต่อ `[u; v; |u−v|]` ได้ 3d = 2,304 มิติสำหรับ d = 768 (สไลด์ 17)
12. ผิด: regression ของ SBERT ใช้ label 0-5 ตรง ๆ กับ cos(u,v) -> ถูก: normalize label เป็น [0,1] เพราะ cos ไม่เกิน 1 แล้วใช้ MSE (สไลด์ 23)
13. ผิด: classification head ของ SBERT ใช้ตอน inference เพื่อให้คะแนนความคล้าย -> ถูก: head ใช้ตอนเทรนเท่านั้น ตอน inference เทียบ u กับ v ด้วย cosine (สไลด์ 14 รูปเปเปอร์)
14. ผิด: Triplet loss เป็นบวกเสมอ -> ถูก: L = max(0, d(a,p) − d(a,n) + α) เป็น 0 เมื่อ d(a,p) + α ≤ d(a,n) และเมื่อ L = 0 ตัวอย่างนั้นไม่มีผลต่อการอัปเดต (สไลด์ 27)
15. ผิด: easy negative ให้ gradient ใหญ่ที่สุดและเทรนมีประสิทธิภาพที่สุด -> ถูก: easy negative ได้ L = 0 ไม่ได้เรียนรู้ ส่วน semi-hard สมดุลที่สุด (สไลด์ 28)
16. ผิด: margin ranking loss ใช้ distance โดยตรงและไม่เกี่ยวกับ triplet -> ถูก: ใช้ similarity และเท่ากับ triplet เมื่อ d = 1 − sim (สไลด์ 29)
17. ผิด: MNRL ต้องระบุ hard negative ทุกตัวเอง และ τ สูงทำให้ขอบตัดสินแข็ง -> ถูก: MNRL ใช้คู่อื่นใน batch เป็น negative ฟรี (N−1 ตัว) และ τ ต่ำทำให้ softmax คมขึ้น (สไลด์ 30)
18. ผิด: SimCSE แบบ unsupervised ต้องใช้ label ของ NLI -> ถูก: ส่งประโยคเดียวกันผ่าน BERT สองรอบด้วย dropout mask ต่างกันเป็น positive pair ได้ ~76.3 โดยไม่ใช้ label (สไลด์ 24)
19. ผิด: dot product ให้อันดับเดียวกับ cosine เสมอ -> ถูก: เท่ากันเฉพาะเมื่อ L2-normalize แล้ว ถ้าไม่ normalize ถูกขนาดเวกเตอร์ครอบงำ (สไลด์ 10, 42)
20. ผิด: `IndexFlatIP` ใช้ได้ถูกต้องกับเวกเตอร์ที่ไม่ normalize เพราะ `.encode()` ของทุกโมเดล normalize ให้อยู่แล้ว -> ถูก: ค่าเริ่มต้นของ `normalize_embeddings` เป็น False และ normalize ด้วย `faiss.normalize_L2` เองเสมอ (สไลด์ 21, 41, เดโม)
21. ผิด: HNSW มีเวลาค้น sublinear เป็นการรับประกันทางทฤษฎี -> ถูก: เป็นผลเชิงสังเกต (≈) ขึ้นกับ efSearch การสร้างกราฟ และข้อมูล ต้องวัด Recall@k และ latency (สไลด์ 40)
22. ผิด: ANN ใช้เปรียบเทียบความเร็วอย่างเดียวก็พอ -> ถูก: ไม่ถูกต้องที่จะเทียบความเร็วโดยไม่รายงาน Recall@k (สไลด์ 39)
23. ผิด: Recall@k = จำนวนที่พบ / k -> ถูก: Recall@k = |Retrieved_k ∩ Relevant| / |Relevant| ส่วนการหารด้วย k คือ precision@k (สไลด์ 37)
24. ผิด: MRR คือค่าเฉลี่ยของ 1/rank ของเอกสารถูกต้องทุกฉบับในทุก query -> ถูก: ใช้เฉพาะเอกสารถูกต้องอันแรกของแต่ละ query แล้วเฉลี่ย 1/rank (สไลด์ 37)
25. ผิด: เวกเตอร์ 1 ล้านตัว 768 มิติ float32 ใช้ประมาณ 768 MB -> ถูก: 10⁶ × 768 × 4 = 3.072 GB ≈ 3 GB (สไลด์ 36)
26. ผิด: สำหรับ corpus ระดับพันล้านควรใช้ HNSW เพราะ recall สูงสุด -> ถูก: เกณฑ์ของสไลด์คือ corpus < 1M ใช้ HNSW และ > 1B ใช้ IVF+PQ (ประหยัด RAM) (สไลด์ 39)

### ตัวอย่าง 1: ขนาดเวกเตอร์ c และจำนวนพารามิเตอร์ของ W

สูตร: c = [u; v; |u−v|] มี 3d มิติ และ W มี (3d) × K ตัวเมื่อมี K label (NLI มี K = 3)

| โมเดล | d | มิติของ c = 3d | จำนวนตัวของ W = 3d × 3 |
|---|---|---|---|
| all-MiniLM-L6-v2 | 384 | 1,152 | 3,456 |
| BERT-base, all-mpnet-base-v2 | 768 | 2,304 | 6,912 (บวก bias 3 ตัวเป็น 6,915) |
| bge-large-en-v1.5 | 1,024 | 3,072 | 9,216 |

- เปลี่ยนจาก d = 768 เป็น 1,024 จำนวนตัวของ W เพิ่ม 9,216 − 6,912 = **2,304 ตัว**
- ตัวหลอก: 1,536 = `[u; v]` (2 × 768), 768 = มิติของ u เดี่ยว, 3,072 = 4 × 768 (นับผิดเป็นสี่ส่วน) หรือ 3 × 1,024 (ถูกถ้า d = 1,024)

### ตัวอย่าง 2: เวลาเทียบทุกคู่ด้วย cross-encoder เทียบ bi-encoder

สูตร: จำนวนคู่ = n(n−1)/2, เวลา cross = จำนวนคู่ × เวลาต่อคู่, เวลา bi (ส่วน encode) = n × เวลาต่อประโยค

| n | จำนวนคู่ n(n−1)/2 | เวลาต่อ forward | เวลา cross-encoder | เวลา encode ของ bi-encoder |
|---|---|---|---|---|
| 1,000 | 499,500 | 5 ms | 2,497.5 s = 41.625 นาที | 1,000 × 5 ms = 5 s |
| 2,000 | 1,999,000 | 4 ms | 7,996 s = 2.221 ชั่วโมง | 2,000 × 4 ms = 8 s |
| 10,000 | 49,995,000 | 5 ms | 249,975 s = 69.44 ชั่วโมง | 10,000 × 5 ms = 50 s |

วิธีทำแถว n = 10,000 ทีละขั้น

1. จำนวนคู่ = 10,000 × 9,999 / 2 = 99,990,000 / 2 = 49,995,000 ≈ 5.0 × 10⁷
2. เวลา = 49,995,000 × 5 ms = 249,975,000 ms = 249,975 s (หรือประมาณ 5 × 10⁷ × 5 × 10⁻³ s = 2.5 × 10⁵ s)
3. เปลี่ยนเป็นชั่วโมง 249,975 / 3,600 = 69.44 ชั่วโมง ตรงกับ "~69 ชั่วโมง" ของสไลด์ 7
4. ฝั่ง bi-encoder: dot product 49,995,000 ครั้งที่ระดับ 1 ns ใช้ประมาณ 0.05 s (ที่ 10 ns ประมาณ 0.5 s) ซึ่งน้อยกว่า 1 วินาทีตามสไลด์ 8

ตัวหลอกที่ผมเห็นในชุดฝึกซ้อม: ใช้ n² = 4,000,000 คู่แทน n(n−1)/2 (ได้ 4.44 ชั่วโมงแทน 2.22 ชั่วโมงของแถว n = 2,000) และคลาดเลขยกกำลัง 10 (0.22 หรือ 22.2 ชั่วโมง)

### ตัวอย่าง 3: Retrieve-then-Rerank เร็วกว่าเท่าไร

โจทย์ตั้งต้น: คลัง 1,000,000 เอกสาร, cross-encoder ใช้ 5 ms ต่อคู่ (query, doc) ระบบ B ใช้ bi-encoder (เวกเตอร์เอกสารเตรียมไว้แล้ว) encode query 5 ms + ค้น FAISS 2 ms แล้ว rerank top-100 ด้วย cross-encoder

- ระบบ A (cross-encoder ทุกเอกสาร) = 1,000,000 × 5 ms = 5,000,000 ms = 5,000 s ≈ 83.3 นาที
- ระบบ B = 5 + 2 + 100 × 5 = 507 ms
- อัตราส่วน = 5,000,000 / 507 = 9,861.9 ≈ **9,862 เท่า** (ไม่ใช่ 986 หรือ 98,600 ซึ่งคลาดเลขยกกำลัง 10 และไม่ใช่ 100 เท่า)

### ตัวอย่าง 5: เวลา brute-force ต่อ query

### ตัวอย่าง 6: Triplet loss

สูตร: `L = max(0, d(a,p) − d(a,n) + α)`

**6a. ตัวอย่างสไลด์ 32** a = [0.3, 0.7, 0.1], p = [0.35, 0.65, 0.15], n = [0.8, 0.2, 0.5], α = 0.5

1. a − p = (−0.05, 0.05, −0.05) → ผลรวมกำลังสอง = 0.0025 × 3 = 0.0075 → d(a,p) = √0.0075 = 0.0866 ≈ 0.087
2. a − n = (−0.5, 0.5, −0.4) → 0.25 + 0.25 + 0.16 = 0.66 → d(a,n) = √0.66 = 0.8124 ≈ 0.812
3. L = max(0, 0.087 − 0.812 + 0.5) = max(0, −0.225) = **0** (เงื่อนไข zero-loss: d(a,p) + α = 0.587 ≤ 0.812)
4. hard negative n′ = [0.32, 0.68, 0.12]: a − n′ = (−0.02, 0.02, −0.02) → d = √0.0012 = 0.0346 ≈ 0.035 → L = 0.087 − 0.035 + 0.5 = **0.552**
5. ถ้า α = 1.0 กับ negative ตัวแรก: L = 0.0866 − 0.8124 + 1.0 = **0.2742** (มากกว่า 0) เพราะ margin ใหญ่ขึ้น negative เดิมกลายเป็น "ไม่ไกลพอ" ถ้า α = 0.5 ต้องมี d(a,n) ≥ 0.0866 + 0.5 = 0.5866 จึงได้ L = 0

**6b. คำนวณตรง ๆ**

- d(a,p) = 0.4, d(a,n) = 0.7, α = 0.5 → 0.4 − 0.7 + 0.5 = **0.2**
- d(a,p) = 0.20, d(a,n) = 0.55, α = 0.50 → **0.15**
- d(a,p) = 0.1, d(a,n) = 0.2, α = 0.5 → **0.4**
- d(a,p) = 0.1, d(a,n) = 0.9, α = 0.5 → 0.1 − 0.9 + 0.5 = −0.3 → **0**
- ตัวหลอก: ใส่เครื่องหมายสลับ (เช่น d(a,n) − d(a,p) + α) หรือลืม max(0, ...)

**6c. ระยะ Euclidean** a = (0, 0), p = (0.3, 0.4), n = (0.6, 0.8), α = 0.8

- d(a,p) = √(0.09 + 0.16) = √0.25 = **0.5**
- d(a,n) = √(0.36 + 0.64) = √1.00 = **1.0**
- L = 0.5 − 1.0 + 0.8 = **0.3**
- ชนิดของ negative: 0.5 < 1.0 < 0.5 + 0.8 = 1.3 จึงเป็น **semi-hard**

**6d. จำแนกสาม negative** d(a,p) = 0.3, α = 0.5: n₁ (0.2) เป็น hard, L = 0.6; n₂ (0.5) เป็น semi-hard, L = 0.3; n₃ (0.9) เป็น easy, L = 0

### ตัวอย่าง 7: Margin Ranking Loss กับ cosine และการเทียบสาม loss

**7a.** a = [3, 4], p = [4, 3], n = [5, 12], α = 0.5

- cos(a,p) = (12 + 12) / (5 × 5) = 24/25 = **0.96**
- cos(a,n) = (15 + 48) / (5 × 13) = 63/65 = **0.9692**
- L = sim(a,n) − sim(a,p) + α = 0.9692 − 0.96 + 0.5 = **0.5092** (n เกือบขนานกับ a จึงเป็น hard negative) ระวังว่าคือ 0.5092 ไม่ใช่ 5.092

**7b.** a = [1, 0], p = [0.8, 0.6], n = [0, 1] ที่ต่างกันตาม metric

- cos(a,p) = 0.8 และ cos(a,n) = 0
- (i) Triplet แบบ cosine distance, α = 0.5: d(a,p) = 0.2, d(a,n) = 1 → 0.2 − 1 + 0.5 = −0.3 → **0**
- (ii) Margin ranking, α = 0.5: 0 − 0.8 + 0.5 = −0.3 → **0** (เท่ากับ (i) เพราะ d = 1 − sim)
- (iii) Triplet แบบ Euclidean, α = 1: d(a,p) = √(0.04 + 0.36) = 0.6325, d(a,n) = √2 = 1.4142 → 0.6325 − 1.4142 + 1 = **0.2182** (มากกว่า 0) ข้อสรุป: metric และ margin เป็นส่วนหนึ่งของ loss

**7c. margin ใหญ่เกินช่วง** ใช้ cosine distance, α = 1.5, cos(a,p) = 0.4: d(a,p) = 0.6, L = 0.6 − d(a,n) + 1.5 = 2.1 − d(a,n) และ d(a,n) มากสุด 2 (เมื่อ cos(a,n) = −1) จึง L ต่ำสุด = **0.1** ไม่มีวันเป็น 0

### ตัวอย่าง 8: cosine ของเวกเตอร์สไลด์ 11

s₁ = [0.91, 0.38, 0.15], s₂ = [0.89, 0.41, 0.19], s₃ = [0.90, 0.39, 0.17]

- cos(s₁, s₂) = **0.9985**, cos(s₁, s₃) = **0.9997**, cos(s₂, s₃) = **0.9996**
- ทั้งสามค่าใกล้ 1 เท่ากัน แม้ s₁ ("The cat sat on the mat.") กับ s₂ ("I love machine learning.") ไม่เกี่ยวกัน นี่คืออาการของ narrow cone: cosine แยกไม่ออก ส่วนตัวอย่างที่ไม่ normalize และอันดับของสามเมตริกอยู่ที่หัวข้อ 3

### ตัวอย่าง 9: masked mean pooling แล้วสร้าง c

H_A = [[2, 4], [4, 8], [100, 100]], H_B = [[1, 3], [7, 5], [40, 40]] (d = 2), แถวที่ 3 ของทั้งสองเป็น `[PAD]` mask = [1, 1, 0]

1. u = ([2, 4] + [4, 8]) / 2 = **[3, 6]** (หารด้วย Σ m = 2 ไม่ใช่ 3)
2. v = ([1, 3] + [7, 5]) / 2 = **[4, 4]**

4. c = [u; v; |u−v|] = **[3, 6, 4, 4, 1, 2]** (6 = 3d เมื่อ d = 2)

ถ้าไม่ใช้ mask: เฉลี่ยทั้งสามแถวได้ u = [35.33, 37.33] และ v = [16, 16] ซึ่งถูก `[PAD]` ลากไปไกล ตัวหลอก: ลืมค่าสัมบูรณ์ (ได้ [−1, 2]) หรือหารด้วย 3

### ตัวอย่าง 10: MNRL

**10a. จำนวน negative:** batch N = 128 → 127 ต่อ query, N = 256 → 255 ต่อ query (N − 1 ไม่ใช่ N)

**10b. ผลของ batch size ต่อหนึ่ง epoch** ข้อมูล 1,024,000 คู่ ใช้เป็น query ครั้งละหนึ่งครั้ง เทียบ N = 32 กับ N = 256

- N = 32: negative ต่อ query = 31 → ทั้ง epoch = 1,024,000 × 31 = 31,744,000 คู่ (query, negative) (3.2 × 10⁴ step)
- N = 256: negative ต่อ query = 255 → 1,024,000 × 255 = 261,120,000 คู่ (4 × 10³ step)
- อัตราส่วน = 255/31 = 8.2258 ≈ **8.23 เท่า** (ไม่ใช่ 8.00 ที่ได้จาก 256/32 และไม่ใช่ 64 ซึ่งเป็นอัตราส่วนขนาดตาราง N × N ต่อ 1 step)

**10c. ค่า loss ของตัวอย่างสมมติ** sim(q,p) = 0.8, negative สองตัว sim = 0.2 และ 0.1

- τ = 1: e^0.8 = 2.2255, e^0.2 = 1.2214, e^0.1 = 1.1052 ผลรวม = 4.5521 → P = 2.2255/4.5521 = 0.4889 → L = −ln 0.4889 = **0.7156**
- τ = 0.1: sim/τ = 8, 2, 1 → e⁸ = 2,980.96, e² = 7.389, e¹ = 2.718 ผลรวม = 2,991.07 → P = 0.99662 → L = **0.0034**

### ตัวอย่าง 11: ทำไม label ของ STS ต้อง normalize

batch มี 4 คู่ label = 5.0, 4.0, 1.0, 0.0 และใช้ loss = MSE ระหว่าง cos(u,v) กับ label โดยไม่ normalize label

- cos อยู่ใน [−1, 1] จึงใกล้ label ได้ที่สุดที่ min(label, 1): label 5.0 → cos 1 error² = 16, label 4.0 → cos 1 error² = 9, label 1.0 → cos 1 error² = 0, label 0.0 → cos 0 error² = 0
- MSE ต่ำสุด = (16 + 9 + 0 + 0) / 4 = **6.25** (หารด้วย 4 คู่ ไม่ใช่ 2) และที่จุดนั้น cos ของสามคู่แรกเป็น 1 เท่ากัน แยกระดับไม่ได้
- ถ้า normalize label (หารด้วย 5) เป็น 1.0, 0.8, 0.2, 0.0 โมเดลปรับ cos ให้เท่ากับ label ได้ครบ MSE ต่ำสุด = **0**

### ตัวอย่าง 12: Recall@k และ MRR

**12a.** Query A มีเอกสารที่เกี่ยวข้อง 4 ฉบับ ถูกจัดอันดับที่ 3, 4, 8, 12 และ Query B มีเอกสารที่เกี่ยวข้อง 2 ฉบับ ถูกจัดอันดับที่ 1, 2

- Recall@10 ของ A = |Retrieved₁₀ ∩ Relevant| / |Relevant| = 3/4 = **0.75** (อันดับ 12 อยู่นอก top-10) ส่วน precision@10 = 3/10 = 0.30 ซึ่งไม่ใช่ recall
- MRR ใช้อันดับของเอกสารถูกต้องอันแรก: A = 3 → 1/3 = 0.3333, B = 1 → 1 ดังนั้น MRR = (0.3333 + 1)/2 = **0.6667**
- วิธีผิดที่ใช้เป็นตัวหลอก: เฉลี่ย reciprocal rank ของเอกสารถูกต้องทุกฉบับก่อน ได้ A = (1/3 + 1/4 + 1/8 + 1/12)/4 = 0.1979 และ B = (1 + 1/2)/2 = 0.75 เฉลี่ย 0.4740 หรือเอาอันดับแรกมาเฉลี่ยก่อนแล้วหาร 1: 1/((3 + 1)/2) = 0.5 ทั้งสองแบบไม่ใช่ MRR

**12b.** อันดับแรกของสาม query คือ 1, 2, 4 → MRR = (1 + 0.5 + 0.25)/3 = 1.75/3 = **0.5833** และอันดับ 4 ให้ reciprocal rank = 1/4 = **0.25**

### ตัวอย่าง 13: threshold กับ anisotropy

กฎ "cosine ≥ 0.40 คือประโยคซ้ำ" ใช้กับ raw BERT ที่ cosine อยู่ใน [0.46, 0.85] (เฉลี่ย 0.58) ค่าต่ำสุด 0.46 สูงกว่า 0.40 จึงทุกคู่ (100%) ถูกตัดสินว่าซ้ำ ไม่ว่าเกี่ยวข้องกันหรือไม่ ส่วน SBERT ซึ่งอยู่ใน [0.1, 0.99] มีที่ว่างให้ threshold แยกคู่ได้
