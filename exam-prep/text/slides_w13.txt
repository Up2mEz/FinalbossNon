What Is an Agent?

· De nition: An autonomous agent is a system where an LLM controls the

   execution ow -- deciding what to do next, calling tools, and iterating until
   the task is complete.


· The Key Distinction:


· Formal View: An agent is a feedback control loop. If the state explicitly

   contains the full interaction history, the transition is Markov with respect to
   that augmented state; a compressed observation may be partially observable.


· Analogy: LLM = Calculator (you type, it answers). Agent = Researcher (asks

   questions, runs experiments, revises hypotheses).

The Anatomy of an Agent

· Four Core Components:


  · 1. LLM Brain (Controller): The reasoning 

      engine -- decides what to do next.


  · 2. Tool Set (Actuators): External functions 

      the agent can call (search, calculator, code execution, APIs).


  · 3. Memory (State): Short-term (context window) + Long-term (persistent

      storage).


  · 4. Planning Module: Task decomposition and strategy selection.


· Data Flow: User Query  LLM Brain  (Plan  Tool Call  Observation) × N

    Final Answer.

Why Agents?

· Already have:
   · Re ection (W11): a loop, but the critic knows only what the writer knows.

   · RAG (W12): fresh facts, but a xed pipeline: retrieve once, then answer.


· Still missing:
   · Grounded veri cation: check against the world (search, run code, tests), not against itself.

   · Live, per-request state: stock price now, order status. Can't be pre-indexed.

   · Model-chosen control ow: decide whether, what, and how many times to retrieve or act.

   · Side e ects: execute code, call APIs, write to a database.


· The Agent Solution: the LLM picks the next action in a loop, and the observation comes from a

   tool, not from itself.


· Key Insight: The LLM doesn't become smarter -- it becomes more capable through tooling.

ReAct as a Formal State Machine

· State De nition: st = (q, h1:t-1) where q = original query, h1:t-1 = full history of

   (thought, action, observation) tuples.


· Transition Function: st LLM (t, at) env ot  st+1


· Markov Property of the Augmented State: Because st already contains the query and

   full history, it is a su cient state representation:
   

                   P(st+1  st) = P(st+1  st, st-1, ..., s1) under this model.

· Practical Caveat: If we truncate or summarize history, the model receives an

   observation that may omit relevant information; memory management then becomes
   critical.


· Implication: Context window must hold the full trajectory -- memory management is

   critical.

The Tool Call Protocol -- Data Flow

· Step-by-Step Protocol:


· 1.LLM generates a tool call: `{"name": "search_web", "arguments": {"query": "GDP

   Thailand 2024"}}` (slide 16). Only the inner `{"query": ...}` comes from our schema; the outer

   keys are the protocol's (OpenAI `name`/`arguments`, Anthropic `name`/`input`, our demo `Action:

   name[argument]`), learned from ne-tuning or the prompt.


· 2. Parser validates the JSON against the tool schema.


· 3. Dispatcher routes to the correct tool function.


· 4. Tool executes and returns a string result.


· 5. Result is appended as an Observation and the loop continues -- the LLM sees it in its next prompt.


· Failure Modes:


· Malformed JSON  Parser error  Retry or fail.


· Hallucinated tool name  Tool not found  Error message.


· In nite loop  `max_steps` guard.                                                                        17

The Reliability Problem -- Why We Need Constrained Decoding
· The Problem: LLMs generate text token-by-token. There is no built-in

   guarantee the output will be valid JSON, valid code, or valid anything.


· Real Failure Examples:


· Current Mitigation (Brittle): Regex parsing, retry loops, prompt engineering.

· Better Solution: Constrain the decoding process itself at the logit level.

The Structured Output Problem

· Why is structured output hard? LLMs pick from a vocabulary of ~50,000

   (GPT-2) to over 250,000 (Gemma) tokens at every step, and nothing built-in
   enforces syntactic validity.


· JSON Validity Requirements (all must hold): our tool schema needs an

   object, so it starts with `{`; keys are quoted strings, values are valid types,
   brackets properly nested and closed.


· Failure Rate Is Benchmark-Dependent: Measure valid-JSON and schema-

   valid rates for the chosen model, prompt, decoding settings, and schema; do
   not assume a universal percentage.

Logit-Level Masking -- The Core Idea

· Concept: At each decoding step, before softmax, set the logits of all invalid tokens to -.


·  Mathematical  Formulation:  logiti  =     logiti  if token i   valid

·  After Softmax: P(tokeni) =   elogiti

   · Valid tokens share 100% of the probability mass.


· Result: Relative to a correct grammar­token index, invalid next tokens receive zero

   probability. A full syntax guarantee additionally requires correct parser state, token-pre x

   handling, and valid termination.

Visualizing Logit Masking -- A Worked Example

· Scenario: Generating JSON, current state = `{`. The grammar allows 3 continuations: open

   a key with `"`, close an empty object with `}`, or emit whitespace (JSON permits blanks
   between structural symbols, so `{\n "a": 1}` is legal).


· But the mask works on token ids, not characters. GPT-2's vocabulary is 50,257 BPE

   tokens, and many of them spell one of those 3 continuations.


· 3 grammatical continuations = 69 vocabulary entries: 62 tokens that open a key (`"`, ` "`,

   `":`, `","`, ...), 5 whitespace-only tokens (`\t`, `\n`, `\r`, ` `, `\n\n`), 2 forms of `}` (`}`, ` }`).


· Masked tokens: Everything else -- 50,188 tokens masked to - (99.86% of the

   vocabulary).


· Probability redistribution: Those 69 tokens now share 100% of the probability mass.


· Contrast -- how much masking bites depends on the parser state: inside a string

   (`{"name": "A`) almost nothing is illegal, so 50,146 of 50,257 tokens stay valid and only
   111 are masked.

Context-Free Grammars (CFG) for JSON

· What determines the valid tokens? A formal grammar -- speci cally, JSON can

   be described by a Context-Free Grammar (CFG).


· JSON CFG (Simpli ed BNF):


· Parser State: At each decoding step, the parser tracks its full con guration -- the

   current rule and the stack of enclosing objects/arrays. (A stack is what a plain regex/
   DFA cannot keep; that is the whole reason nesting needs a CFG.)


· Key Insight: At each parser state, the CFG de nes a nite set of valid next tokens

   (the full set of valid continuations can still be in nite).

CFG-Guided Decoding Algorithm

· Algorithm (at each decoding step):


   · 1. Maintain parser state -- not just which rule, but the position inside the rule (`object  '{'

       members? '}'` means the `{` is already consumed) and the stack of unclosed brackets (`{"a":
       {"b": 1` sits two objects deep, so the rst `}` closes the inner one and a second `}` is still legal).


   · 2. Compute valid next tokens -- from the parser state, enumerate all tokens that keep the parse

       valid.


   · 3. Apply logit mask -- set invalid tokens to -.


   · 4. Sample -- draw the next token from the masked distribution.


   · 5. Update parser state -- advance the parser with the selected token.


· Implementation: The `outlines` library by Willard & Louf provides production-ready CFG-guided

   decoding.


· Naive Complexity: Scanning the whole vocabulary at every step costs O( | | ). Precomputed state-to-

   token indices make lookup e cient, but applying a vocabulary mask and the model's output softmax still
   scale with vocabulary size; the whole decoding step is not O(1).

Regular Expression Constraints -- A Simpler Alternative

· For simpler structures: Use Regular Expressions instead of full CFGs.


· Example: Date eld must match `\d{4}-\d{2}-\d{2}` (e.g., `2024-01-15`).


· Method:


   · 1. Compile regex to a Deterministic Finite Automaton (DFA).


   · 2. At each decoding step, use the DFA state to determine valid next tokens.

   · 3. Apply the same - masking technique.


· Advantage: A DFA state transition for one character is constant-time; end-to-end token

   validation and decoding still include tokenizer-pre x lookup, masking, and model computation.


· Limitation: Cannot enforce arbitrarily deep recursion -- balanced nesting to unbounded depth

   is not a regular language. (Nuance worth stating: JSON capped at a xed max depth is regular
   and can be compiled to a DFA -- the state count just blows up. Unbounded depth is what
   forces a CFG/pushdown automaton.)

Three Memory Implementations -- Bu er, Summary, and Retrieval

· Implementation 1 -- Bu er Memory: Append everything, O(n) growth. Simple,

   no loss -- but eventually over ows.


· Implementation 2 -- Summary Memory: when the bu er exceeds a token

   budget, the LLM collapses everything but the last k turns into one summary,

  bounded at O(k × msg + summary) . Bounded -- but summarization is

   lossy.


· Implementation 3 -- Retrieval Memory: Embed + vector-search top-k relevant
  messages. The prompt is bounded at O(k × | msg | ) -- but note the store still

   holds all n turns, so storage stays O(n) and search is O(n) for the brute-force
   scorer we use in the demo (an ANN index makes it sublinear). Relevant -- but
   may miss temporally important items.


· Hybrid Approach (the practical default): Summarize old turns, retrieve relevant

episodes on top. When two rankers disagree about which episodes to pull, fuse

their rankings with RRF from Week 12.                                               31

Bringing It All Together -- The Complete Agent Architecture

· The Complete Agent Architecture (Micro-Level):
  Single Agent = Planning + Memory + LLM + Constraints + Tools


· Execution Flow (How They Interact):

· 1. Planning: Decomposes user query into structured sub-tasks.


· 2. Memory: Retrieves relevant historical context and prior state.


· 3. LLM: Executes the core ReAct reasoning loop (Thought -> Action).


· 4. Constraints: Enforces valid grammar/JSON schema during token generation.


· 5. Tools: Executes real-world action $\rightarrow$ Appends observation back to context.


· Scaling to Teams (Macro-Level):
  Multi-Agent System = Topology × {Agent1, Agent2, ...} + Protocol


· Connects specialized agents via Topologies (Routing, Supervisor, Debate) and
Communication Protocols.

The Reliability Stack (Defense in Depth)

· Layer 1 -- Constrain: Generate only valid grammar or schema shapes.

· Layer 2 -- Validate: Check types, ranges, permissions, and business rules.

· Layer 3 -- Recover: Retry only bounded, recoverable failures with error

   feedback.


· Layer 4 -- Escalate: Require human approval for risky or destructive actions.

· Defense in Depth: No single layer catches every failure mode.

Guardrails & Safety in Agent Systems

· Risk: Agents can a ect external systems, not just generate text.

· In nite Loops: Enforce `max_steps`, time, and token budgets.

· Unauthorized Actions: Use least privilege and explicit allowlists.

· Prompt Injection: Treat tool content as untrusted data, not instructions.

· Code Execution: Use isolation, resource limits, and controlled interfaces.

· High-Impact Actions: Pause for human con rmation and keep an audit log.
