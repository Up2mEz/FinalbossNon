Act I ­ The Hardware Wall

· Theoretical elegance meets physical limits.


· The GPU Memory Hierarchy:


  · SRAM (L1/L2 Cache): Ultra-fast,

      extremely small (~50 MB).


  · VRAM (HBM on datacenter cards,

      GDDR on T4/RTX): Fast, limited capacity


  · System RAM: Slow, large capacity

      (Terabytes).


· The Goal: Keep data in VRAM and

   compute.

The 1-Parameter Footprint

· How much space does one parameter take?

  · FP32 (Single Precision): 32 bits = 4 bytes (The old standard).

  · FP16 / BF16 (Half Precision): 16 bits = 2 bytes (The modern default).

  · INT8 (Quantized): 8 bits = 1 byte.

  · INT4 (Highly Quantized): 4 bits = 0.5 bytes.


· The Golden Rule: For modern LLMs, assume base weights are in FP16 or

   BF16.


· Formula: Mw = N × 2 bytes (where N is parameter count).

Beyond Weights -- The Hidden Memory Costs

· Weights are just the beginning. During inference, memory goes to:

  · 1. Model Weights: Static (FP16 = 2N bytes).

  · 2. KV Cache: Dynamic, grows with sequence length and batch size!

  · 3. Activations: Temporary tensors passed between layers.

  · 4. Workspace / Overhead: Memory allocated for CUDA kernels and the

      OS.


· The Equation: Total Inference VRAM = Mw + MKV + Mact + Moverhead

· Why BF16 Matters for Training:


· FP16 max value is  ± 65,504. Gradient spikes can easily over ow!

· BF16 max value is  ± 3.4 × 1038 (same as FP32!). Far lower over ow risk -- not zero.

· Trade-o : BF16 trades precision (mantissa) for range (exponent).


· Rule of Thumb: Train in BF16; at inference keep the model's native dtype, or FP16/INT8 if it

   was trained/validated in that range.


· Hardware requirement: Native BF16 tensor-core support needs Ampere or newer (A100, RTX

   30xx+, H100). Older cards like the T4 (Turing) have no native BF16 -- use FP16 instead on T4.

Operational Metrics: TTFT vs. TPS

· How we measure LLM speed in Production:

· 1. Time To First Token (TTFT): How long before the user sees the rst word?


   · TTFT = Network Latency + Pre ll Time + Decode Time (1st token)

   · For long prompts Pre ll usually dominates this sum, so TTFT is mostly a Pre ll measurement

      (plus queueing under load).


   · Crucial for perceived responsiveness (users perceive >500 ms as "lag").

· 2. Tokens Per Second (TPS) / Decode Rate: How fast the text streams out?


   · Determined by the Decode phase memory bandwidth.

   · Human reading speed  4­5 words/sec; >10­15 TPS feels instantaneous to the user.

· Optimization Trade-o s: Some techniques improve TTFT but hurt TPS, or vice versa (e.g.,

   Speculative Decoding improves TPS; chunked pre ll improves TPS/inter-token latency for
   ongoing requests at the cost of TTFT for the new request).

The Training Memory Explosion

· Inference is cheap. Training is astronomically expensive.

· The "16N" accounting (FP16 weights + Adam, no sharding): Training requires

   16×Params bytes just for model states.

  · Weights (2N) + Gradients (2N) + Optimizer States (12N)

  · The Optimizer (Master Weights, Momentum, Variance) 

      consumes 75% of the memory!


· Example: LLaMA-3 8B


  · 8B × 16  128 GB

  · Exceeds a single 80GB H100 GPU (Activations not even included yet).

  Gradient Checkpointing

    · The Activation Memory Problem:

      · Backpropagation requires saving all forward 
         pass activations to compute gradients. This memory scales O(L) with layers.


    · The Solution: Gradient Checkpointing

      · Save activations only at speci c "checkpoint" layers (e.g., every L-th layer  every 6th of 32).

      · During backprop, if an activation is missing, recompute it on-the- y from the

           nearest checkpoint.


    · The Trade-o :


      · Memory: Reduced from O(L/k + k) to O( L) when k = L.

      · Compute: Increases training time by  30 % .

Act III ­ The Speed Revolution (FlashAttention & MoE)

· The O(N2) Memory Problem with Standard Attention:


· Recall Week 4: Attention matrix                                             S

S = QKT `[batch, heads, 

seq, seq]`. Size is N × N 

(where N is sequence length).


· For N = 32,000, S takes  2 GB 
  per head. With 32 heads, that's 64 GB just to store the attention matrix!


· The Memory Wall bottleneck: We have to write the N × N matrix to HBM, read
  it back for Softmax, write it to HBM again, then read it back to multiply with V.


· Result: Massive VRAM usage and extreme memory-bandwidth latency.

  FlashAttention -- Tiling and IO-Awareness

   · Goal: Compute exact attention without writing the N × N matrix to slow HBM.

   · Tiling (Inner/Outer Loops): Break Q, K, V into "blocks" that t in the ultra-fast SRAM.


      · Compute partial QKT, compute partial Softmax, multiply by tile of V entirely within SRAM.

   · Write out ONLY the nal output (size N × d) to HBM.

   · The Catch: Softmax requires the global max of 

       the entire row. How do we do Softmax on a tile
       if we don't have the whole row?

The Secret Sauce: Online Softmax

·  The Softmax Problem: Softmax(xi) =   e xi-max(x)

                                                        


                                        exj-max(x)

   · You need the true global maximum of the row to avoid over ow.


· Online Softmax:


   · Keep track of a running maximum (m) and a running sum of exponentials (l) as you

      process each tile.


   · Update rule when moving from tile 1 to tile 2:


     · New max: mnew = max(mold, max(tile2))

     · Rescale previous sum: lnew = lold × emold-mnew +  etile2-mnew

· Result: Exact attention computed in O(N) memory instead of O(N2)! No quality loss.
FlashAttention -- The Backward Pass Mechanics

· The Training Memory Problem: Standard attention requires saving the huge
  N × N matrix for backpropagation.


· FlashAttention Backward Pass:

  · Drops the massive attention matrix entirely during the forward pass.

  · Analytically recomputes the attention block on-the- y in SRAM during the

      backward pass.


· The Magic: Trades a tiny amount of compute for a massive reduction in

   VRAM, making long-context training possible.

MoE Upcycling -- The Researcher's Hack

· The Problem: Training a massive MoE from scratch is too expensive.


· The Upcycling Solution:


· 1. Copy Weights: Take a 

   pre-trained Dense model 

   (Top Box) and copy its 

   Attention/Norm layers directly 

   (Green/Yellow).


· 2. Clone the Experts: Take the 

   single MLP (Blue Box) and make 

   E exact copies of it.


· 3. Add Router: Insert a brand-new Router (Red Box) to manage the experts.


· Result: You get an MoE that is already "smart" on day one. Only the router starts from

   scratch -- then keep training everything.

Act IV ­ The Serving Stack (The Fragmentation Problem)

· Standard KV Cache Allocation (Static):


· Traditional frameworks pre-allocate memory for the maximum possible sequence length (e.g., 4096)

   for every request.


· If a user only generates 50 tokens, the remaining 4046 tokens' worth of memory is locked and wasted.


· Fragmentation:


· Internal fragmentation: Wasted pre-allocated space.


· External fragmentation: Wasted gaps between 

   di erent requests.


· New requests can't t into fragmented free space.


· Real-world Impact: Naively served LLMs use only 20­40% of the KV-cache memory they reserve, due

to fragmentation.

Speculative Decoding -- The Draft-and-Verify Pipeline

· The Autoregressive Bottleneck: Decoding is sequential and memory-bandwidth

   bound. We want to process multiple tokens in parallel (like pre ll).


· Speculative Decoding (Leviathan et al., 2023):


  · Step 1 (Draft): A small, fast draft model (e.g., 1B params) generates 

      candidate tokens sequentially.


  · Step 2 (Verify): The large target model (e.g., 70B params) processes ALL 

      candidate tokens in a single parallel forward pass (acts like a fast pre ll).


  · Step 3 (Accept/Reject): Accept tokens that match target distribution; reject the

      rest.


· Guarantee: Final output is statistically identical to sampling from the target

   model alone. Speedup: ~2­3×.

Quantization Math & Worked Example

· Quantization = Mapping continuous values to discrete levels:

  · q = round (x/s) + z ; s = scale factor, z = zero-point. (z = 0 for symmetric absmax, as below).

  · Absmax Quantization (FP16 -> INT8):

  · FP16 range [-3.2,3.2] -> INT8 range [-127,127].

  · Scale s = 3.2/127 = 0.0252.

  · Value 2.1  round(2.1/0.0252) = 83.

  · Dequantize: 83 × 0.0252 = 2.092 (Error introduced!).


· Block-wise Quantization: Use di erent scales for small blocks (e.g., 64 values) to

   reduce error.

    · QLoRA (Dettmers et al., 2023) -- Three Innovations:


      · 1. 4-bit NormalFloat (NF4): 4-bit data type whose levels follow the normal

      · 2. Double Quantization:

          Over ow optimizer states 
          to CPU RAM to prevent

QLoRA -- Forward & Backward Pass Walkthrough

· Storage: Base weights are locked in 4-bit (NF4) in VRAM.


· Forward Pass (Compute):


   · 1. Dequantize block: from NF4 -> 16-bit on-the- y in SRAM. 

       (FP16 on T4, see Slide 10.)


   · 2. Compute MatMul & Discard: Multiply input, then drop 

       the 16-bit block -- only a small working copy lives in 
       VRAM at a time.


   · 3. Add LoRA path: Add the 16-bit LoRA adapter output 
     (h = Wcomputex + LoRA).


· Backward Pass:


   · Parameter gradients exist only for the LoRA adapters (A, B); 

       activation gradients still ow through the frozen layers.


   · The NF4 base weights are literally just a frozen reference grid.


· Memory Savings: roughly an order of magnitude vs. full FP16 ne-tuning 

   (exact ratio depends on batch, seq len, checkpointing).

Practical PEFT -- The Magic of Modern Libraries

· Under the Hood: Complex math, custom data types (NF4), SRAM/VRAM

   memory management.


· In Practice (Hugging Face `PEFT` & `bitsandbytes`): Just 2 simple steps!

  · 1. Quantize the Base Model: Use `BitsAndBytesConfig` to load the

      massive model in 4-bit (or load a pre-quantized checkpoint).


  · 2. Inject the Adapter: Use `LoraConfig` and `get_peft_model()` to

· The Result: We shrink the training footprint of an 8B model to ~0.17%

   trainable parameters -- it ts a 16 GB T4.

Distillation in Production -- From DistilBERT to Llama 3.2

· DistilBERT (2019): BERT 12  6 layers, init from every other teacher layer. ~40 % smaller, ~60

   % faster, ~97 % of BERT on GLUE dev (benchmark-speci c).


· TinyBERT (layer-by-layer hidden states + attention) / MiniLM (last-layer attention + value

   relations) -- copy the reasoning, not just the answer.


· LLM era -- distillation is the main pipeline for small models:


  · Llama 3.2 1B/3B -- pruned from Llama 3.1 8B, then logit KD from 8B + 70B teachers.

  · Gemma 2 (2B, 9B) -- trained with KD instead of plain next-token loss.

  · DeepSeek-R1-Distill -- SFT on ~800k R1 samples (~600k reasoning + ~200k general).


·  TinyLlama-1.1B is NOT distilled -- pretrained from scratch on ~3T tokens. Small by

   design  small by distillation.


· Decision rule: must t VRAM  quantize (cheap). Must answer fast on edge and you own a

   good teacher  distill.

Summary

· 1. VRAM Bottlenecks: Model Weights scale by precision (FP16 = 2x, INT4 =

   0.5x parameters). But KV Cache grows linearly with batch size and context
   length, becoming the true bottleneck.


· 2. Memory Algorithms: FlashAttention computes attention smartly in SRAM to

  prevent O(N2) blow-up. PagedAttention (vLLM) nearly eliminates KV cache

   fragmentation like an OS page table.


· 3. Training Costs: Full netuning is heavily memory-bound, requiring  16 ×

   parameters in GB (e.g., 128 GB for an 8B model).


· 4. The PEFT Solution: QLoRA freezes the base in 4-bit (NF4) and trains tiny

   LoRA adapters -- <1% trainable. Adapters stack (MAD-X) and steer (O-LoRA).


· 5. Distillation: the only axis that cuts compute -- a shallower student learns the

   teacher's soft targets (Llama 3.2, Gemma 2, R1-Distill).
